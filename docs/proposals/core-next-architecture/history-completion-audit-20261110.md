# Historical-prefix completion audit, 2026-11-10

**Result: production feasibility remains NotEstablished; the strong synchronous contract remains unchanged.** No examined construction has measured evidence for complete Core semantics, actual native/proof correspondence, a genuine historical-prefix certificate and durable publication at whole-request p50 ≤ 50 ms / p95 ≤ 100 ms, with fresh-recipient p95 ≤ 100 ms. This is an evidence conclusion about the inspected candidates, not an impossibility theorem about other constructions or hardware.

This audit used the research skill's primary-source method. It read repository contracts, code and retained receipts, and checked official upstream source/documentation. It performed no builds, proof runs or timing experiments and changed no frozen inputs. It adds only this note. The [architecture decision](architecture-decision-20261107.md), [backend continuation](continuation-20261107.md), [local K study](local-k-20261109.md), [semantic/evidence contract](../../../specs/033-core-proof-feasibility/contracts/semantic-and-evidence.md) and [033 specification](../../../specs/033-core-proof-feasibility/spec.md) govern the conclusions below.

## What the history obligation actually requires

A certificate must establish a checked allowed origin and initialization, followed by every declared finalized transition, ending at the exact independently expected subject. It must establish the semantics of those transitions, not merely bind an ordered collection of bytes. For the requested full-Core outcome, the semantic relation must cover the complete declared Core surface. Passing the narrower G1 template or the November 9 closed local profile cannot establish that broader claim. The contract explicitly distinguishes the G1 subset from full-Core formalization and later production gates. [Sources: contract §§1–3; specification FR-010–FR-012 and scope assumptions.](../../../specs/033-core-proof-feasibility/contracts/semantic-and-evidence.md)

The endpoint must bind origin, release, complete program/profile, live and lifetime-ID state, maintained-view meaning, parent/head and logical event position, exact request/context/result/ordered commands, observation commitment/recipe, phase, obligation frontier and proof-step count. Full application SHA-256 digests remain 256 bits; range checks and canonical encodings are part of the actual relation. A proof's machine-step count is distinct from event count. An unfinished phase, unchecked suffix or producer-selected endpoint cannot close the prefix. Refusal attempts have an independently bound result while leaving committed business history unchanged. [Source: contract §§3–7.](../../../specs/033-core-proof-feasibility/contracts/semantic-and-evidence.md)

There is useful existing mathematics: [History.lean](../../../experiments/transition-study033/proofs/Core033/History.lean) defines checked hops and an initialized prefix and proves scoped exact-history and preservation results. The retained [fresh audit output](../../../specs/033-core-proof-feasibility/evidence/scoped-chain/history-scoped-axioms-fresh.stdout.txt) reports 17 checked targets with fresh kernel replay, explicitly `g1_pass: false` and `concrete_certificate: false`. The module itself says native decoding, concrete commitments and actual Nova embedding must refine its relation. These are conditional/scoped mathematical results; they are not an actual emitted certificate for the November 9 Rust K.

The backend measurements use one worker pinned to one CPU on Xeon X5670. They are not full-request distributions or security-equivalent comparisons. The 47.54 ms STARK consumer observation establishes neither a p95 result nor fast proof production. The native K's measured local interval excludes proof production, cold consumer, disk and network; its larger initialization also took seconds. [Sources: backend continuation and raw-result links](continuation-20261107.md), [local K method and results](../../../experiments/local-k-study-20261109/README.md).

These observations justify keeping the tested full-guest/full-circuit rebuilds out of the claimed synchronous millisecond solution. They do not prove that adding semantics must increase runtime monotonically, nor exclude an unmeasured optimized construction. Any such construction needs its own frozen security, hardware, relation and lifecycle campaign.

## Available cryptographic mechanisms and their limits

**Nova provides a supported incremental construction, not a Core semantic bridge.** Its official description explains incremental proofs over sequential computation; it does not specify absolute Core latency. In the pinned implementation, `RecursiveSNARK::new` performs the first step, the first `prove_step` only updates accounting, and compressed verification returns an endpoint vector. The application must compare that vector with the full independently expected endpoint. For this project the actual K constraint embedding, output wires, codec and native relation must be checked before the existing history theorem applies. [Sources: official Nova overview](https://github.com/microsoft/Nova), [pinned implementation](https://raw.githubusercontent.com/microsoft/Nova/01b1e2d662a847ed7029770ecbaf6687398899dd/src/nova/mod.rs), [local backend contract](../../../specs/033-core-proof-feasibility/research-notes/proof-backend.md).

**RISC Zero supports execution receipts and proof composition.** Version 3.0.6's `Receipt::verify(image_id)` checks the seal and the expected successful execution claim, including journal integrity. This binds execution to an expected image; it does not prove that the guest implements Core. The caller must still compare the complete application journal with its independently expected subject. Checking only receipt integrity or trusting receipt metadata is insufficient. [Source: pinned official receipt implementation.](https://raw.githubusercontent.com/risc0/risc0/v3.0.6/risc0/zkvm/src/receipt.rs)

Composition can connect an established prior receipt to a successor. The pinned guest `env::verify` creates an assumption for the specified image/journal; a final unconditional receipt requires resolution. Official documentation describes resolution during succinct/Groth16 proving. A host claim that a predecessor exists is not equivalent. Guest code must also enforce equality between the predecessor's proven endpoint and its own exact starting subject. Composition contributes no missing K correctness and no measured Core production speed. [Sources: pinned guest verification implementation](https://raw.githubusercontent.com/risc0/risc0/v3.0.6/risc0/zkvm/src/guest/env/verify.rs), [official proof-composition documentation](https://dev.risczero.com/api/zkvm/composition).

Neither mechanism currently closes the strong obligation with measured project evidence. A chain of hashes binds bytes; a signature adds a named signer's authority. Neither by itself establishes checked genesis or execution semantics. An identity receipt proves execution of its identity relation. A producer's `ValidBasis` boolean, serialized native object or assumed K invariant cannot establish a fresh recipient's history. Async batching, later certification, replay by the recipient or a trusted checkpoint changes acceptance/finality or trust premises; none is silently substituted for the existing contract. [Sources: architecture decision's validity/finality sections](architecture-decision-20261107.md), [contract §§2–7](../../../specs/033-core-proof-feasibility/contracts/semantic-and-evidence.md).

## A bounded next implementation that adds genuine correctness

The next useful implementation is an explicitly separate **small-profile prefix correctness experiment**, not a production feasibility pass. Keep its source, inputs, evidence and budget separate from the frozen studies. First finish the machine-checked initialization/preservation and actual native-source/codec correspondence for the exact closed K profile being certified. A matching model or shared source file alone does not close that bridge. The actual guest/circuit must then be connected to that checked relation. [Required bridge criteria.](../../../specs/033-core-proof-feasibility/research-notes/formal-correspondence.md)

One supported realization to investigate is a pinned RISC Zero 3.0.6 guest that performs checked initialization and two real finalized K transitions, using the existing full SHA-256 authenticated state profile. Start with a tiny declared genesis and create then set, with emit and refusal controls separately exercised. The guest must compute/check the actual relation and full public endpoint; a host boolean, host-computed commitment beside an unrelated proof, or copying expected output into the journal is disallowed. A single guest checking the complete bounded prefix is a legitimate first correctness experiment; it makes no incremental-cost claim. Later composition may replace repeated-prefix execution only after its predecessor and assumption-resolution obligations are implemented and checked. This is a construction proposal inferred from the official APIs above, not a completed experiment or a promised runtime.

Its fresh consumer must need only independently trusted release/image/verifier material, the expected full subject and the certificate. Remove repository/history access and all authoritative Core evaluation/replay from the consumer's acceptance path. Prove and retain the actual certificate; disable development/Fake acceptance and require the selected succinct profile. The guest's own real checked initialization/transitions are the proof computation, not a fresh verifier's replay fallback. Preserve source/build/ELF/image identities, effective SDK features/parameters, exact codecs, raw execution/verification evidence and all explicit trust assumptions. [Sources: contract §§3–7](../../../specs/033-core-proof-feasibility/contracts/semantic-and-evidence.md), [existing pinned STARK experimental profile](../../../experiments/stark-preflight-20261107/README.md).

This milestone can establish a cryptographic prefix for a named small executable profile once its formal bridges and controls pass. Without those bridges, report only a receipt for that guest's execution. Either outcome must retain full-Core correctness and strong performance as NotEstablished. Do not interpret the proposal as authorization to spend unbounded build/proving time or as reversing the measured decision against expensive full-Core guest conversion.

The original workload matrix remains populations 128/2048/8192, histories 1/128/8192 and lifetime inventories N/16N/128N under established origin, with the separately bound cap1000 boundary and bounded operation sizes/affectedness. No single closed-profile warm set distribution discharges that matrix. Prefix validity also does not establish latest-head freshness, current authorization, data availability or physical external command delivery. [Source: specification FR-014–FR-021, SC-001–SC-009 and workload/authority assumptions.](../../../specs/033-core-proof-feasibility/spec.md)

**Decision:** continue exact K/native correctness and durable-publication work; permit only explicitly scoped correctness research on a genuine prefix adapter. Keep full Core, full correspondence, cryptographic prefix completion and the complete synchronous performance gate separately visible until each has actual passing evidence. The present audit closes none of those gates by renaming local execution or identity receipts.

## Source follow-up: smallest real local-K guest

This follow-up read the exact [auth.rs](../../../experiments/local-k-study-20261109/auth.rs), [kernel.rs](../../../experiments/local-k-study-20261109/kernel.rs), [planner.rs](../../../experiments/local-k-study-20261109/planner.rs), [old guest manifest](../../../experiments/stark-preflight-20261107/guest/Cargo.toml), [build wrapper](../../../experiments/stark-preflight-20261107/build_guest.py) and [client](../../../experiments/stark-preflight-20261107/client/src/main.rs). **No compilation or execution was performed; successful compilation of these exact dependencies remains unestablished.** Source inspection supports a small std guest without replacing K's logic:

- Set `risc0-zkvm = { version = "=3.0.6", default-features = false, features = ["std"] }`; use ordinary `fn main()`. Partial std and automatic entrypoint linkage are explicitly supported. Retain the pinned serde/serde_json dependencies and source edition; these modules use allocation, collections and JSON rather than OS services. The prior no_std identity manifest alone is insufficient. [Official guest module, lines 63–67 and 107–114](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkvm/src/guest/mod.rs#L63), [official std JSON guest manifest](https://github.com/risc0/risc0/blob/v3.0.6/examples/json/methods/guest/Cargo.toml).
- `std::sync::Arc` is not inherently excluded by rv32im: the installed toolchain's official target declares 64-bit maximum atomics, CAS and single-thread execution. The SDK lowers atomics to ordinary operations with `-C passes=lower-atomic`; the old wrapper already supplies this flag. This is a single-thread guest construction, not a claim of multithreading support. [Official r0.1.97.0 target, lines 22–36](https://github.com/risc0/rust/blob/r0.1.97.0/compiler/rustc_target/src/spec/targets/riscv32im_risc0_zkvm_elf.rs#L22), [official SDK flags, lines 421–456](https://github.com/risc0/risc0/blob/v3.0.6/risc0/build/src/lib.rs#L421).
- Plain `sha2` remains the exact native dependency option. For the official accelerator, `use risc0_zkvm::sha::{Impl, Sha256}; Impl::hash_bytes(bytes)` returns `Self::DigestPtr`; copy `digest.as_bytes()` into `[u8; 32]`. The trait specifies full SHA-256 padding/trailer, whereas `hash_pair` and `hash_raw_data_slice` have different meanings. [SHA trait, lines 66–112](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkp/src/core/hash/sha/mod.rs#L66). The guest implementation invokes `sys_sha_buffer`/`sys_sha_compress`; its `hash_bytes` adds the standard trailer. Keep each message length within its u32 bit-length arithmetic; the bounded K messages are far smaller. [Guest implementation, lines 178–224](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkp/src/core/hash/sha/guest.rs#L178).
- `Digest::as_bytes()` exposes all 32 underlying digest bytes; do not re-encode its numeric words with guessed endian conversions. The official RustCrypto wrapper copies those same bytes into a 32-byte output and exports a cross-compatible SHA type. [Digest, lines 86–94](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkp/src/core/digest.rs#L86), [wrapper, lines 119–141 and 168–169](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkp/src/core/hash/sha/rust_crypto.rs#L119).

To keep **auth.rs and kernel.rs byte-identical**, a new small external adapter crate can re-export `risc0_zkvm::sha::rust_crypto::{Digest, Sha256}`. Give that adapter a distinct package name and use the guest dependency key `sha2` for it; the existing `use sha2::{Digest, Sha256}` then resolves explicitly to the adapter. The exported SHA type is the official `rust_crypto::Sha256<sha::Impl>`, whose implementation selects the guest accelerator. Do not globally patch crates.io `sha2`: the SDK has its own dependency on that package. This adapter changes the effective hashing implementation/build profile even though the K source bytes remain identical; record and check that boundary. An alternative is a separately frozen auth.rs import/body adaptation directly using `Impl`; that has different source bytes. Neither approach establishes a formal native/guest equivalence. [Official SHA exports, lines 46–53 and 99–105](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkvm/src/sha.rs#L46), [SDK dependency, line 60](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkvm/Cargo.toml#L60).

The smallest useful fixed scenario starts with **live a.x=1, used={a}, cap=2**, then creates b and sets a from 1 to 3. Keep the seed, cap and two requested operations fixed in the guest or bind them completely in its journal. Read two bounded proposal byte buffers, call the actual `decode_proposal`, then `Kernel::new`, `initialize` and `Kernel::check` twice in order using each returned `Checked.next`. Construct requests from the established basis with fixed request IDs. Compile the original modules using explicit source paths, so kernel.rs's relative `include_str!` still binds the original reference fixture. Include that fixture in the build-input freeze. Freeze effective serde_json features as well as its version: this actual K hashes serialized JSON for several commitments. Planner supplies witnesses on the host and is **absent from the guest**; K independently checks both proposals, their requested effects, full authenticated paths, result projections and resulting roots. Run all these checks as ordinary proved guest execution, never inside the SDK's unconstrained-execution facility.

Bound lengths before allocating buffers (each proposal ≤262144 bytes), rather than deserializing an unbounded host Vec first. Commit the profile tag, complete initial/final views, exact requests and both ordered outcomes; the independent consumer compares the entire expected journal plus trusted image. The local head remains this profile's diagnostic chain identity, not the canonical Core EventId. The old client must lose its identity-only `initial == expected` condition and 43-word decoder; its V1COMPAT packaging, strict receipt framing, succinct-only check, dev-mode-disabled verification and independent expected-image/journal checks remain useful patterns. [Official guest I/O signatures](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkvm/src/guest/env/mod.rs), [existing client](../../../experiments/stark-preflight-20261107/client/src/main.rs).

Initialization work is real even for this tiny case. From the current source, `Auth::new` computes two empty leaves and **512 empty-ladder branches**. Each one-row seed tree then computes its address, leaf and 256 branches. Counting only the guest calls above gives 515 hashes in `Kernel::new`, 517 in one-row initialization, 1034 in accepted create and 518 in accepted set: **2584 SHA calls** before any additional output hashing. These are source operation counts, not guest-cycle or latency measurements. No host-precomputed empty ladder may silently replace the actual checked constructor. The SDK's default bump allocator also does not reclaim allocations; bound this experiment rather than infer unlimited-history memory behavior. [Local authentication/kernel sources above; official allocator feature description, lines 169–171.](https://github.com/risc0/risc0/blob/v3.0.6/risc0/zkvm/Cargo.toml#L169)

The existing private compiler wrapper is `/data/repos/behavior-ir-core-033/experiments/stark-preflight-20261107/risc0/toolchains/v1.97.0-rust-x86_64-unknown-linux-gnu/bin/rustc`; its original ELF is adjacent as `rustc.verified-elf`, and its target library directory contains `libstd`. Read-only inspection confirmed those files. **The old build_guest.py has no new-root option** and writes fixed old result paths; do not rerun or edit it for this experiment. A new wrapper can reuse that compiler path and exact flags, while accepting separate manifest/target/results/cache paths and using a new locked dependency graph. Keep all Cargo/cache/result writes in the new study; initialize its private dependency cache separately. The command shape remains `cargo build --offline --locked --release --target riscv32im-risc0-zkvm-elf --manifest-path NEW_GUEST/Cargo.toml --target-dir NEW_TARGET`. Freeze transitive local module/fixture/adapter inputs and compiler/loader provenance, and package the resulting user ELF with V1COMPAT into a new combined program/image. [Existing build wrapper](../../../experiments/stark-preflight-20261107/build_guest.py), [official guest build and packaging, lines 155–175 and 573–592](https://github.com/risc0/risc0/blob/v3.0.6/risc0/build/src/lib.rs#L155).
