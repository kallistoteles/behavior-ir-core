# Native329 and actual344: standard-library source binding

Research only, 2026-11-19, using the research skill and existing local primary records/source. This investigation writes only this new note. It ran no builds, tests, downloads, network requests, archive scans, binary verification, or process argument/environment inspection, and did not access the protected proof artifacts. Actual345/root91401 was supplied as live; no outcome is inferred. Hashes below are either explicitly attributed existing receipts or newly computed hashes of ten small analysis source files, not fresh verification of the compiler/runtime binaries.

## Finding

**Native329 and actual344 use demonstrably different compiler and standard-library artifact identities. The particular I/O source bodies cannot presently be compared across those identities from the inspected local sources.** Native329 used stable Rust 1.98.1, commit `48a229ceaefd4985c50990b14116b6d856af0985`; actual344 used nightly Rust 1.100.0, commit `923c95cdf5ba65cea505aa2ea829f578e1506ed8`. Both target the GNU Linux x86-64 host. The available I/O sources belong to the second tuple. A version difference alone proves neither that a particular default body changed nor that it remained equivalent.

The caveat in [io-default-model-boundary.md](io-default-model-boundary.md:87) is therefore material. Its links described as “native default body” identify **analysis-sysroot source**, suitable for analyzing the extracted function but not yet a bound source body for the stable native329 executable. This note resolves the tuple/artifact identities and available source provenance; it does not discharge the missing native source/model correspondence. [T049 and T051](../tasks.md:109) distinguish the analysis tuple and require real stable/extraction source/cfg/tool differences to be bound.

## Cfg/source differences: what is and is not established

The frozen native executor [sets](../evidence/v2/w001/subjects/r9273/sources/00323:455) `-C target-cpu=x86-64`, the pinned GCC-wrapper linker and zero dev/test debug information. Both retained native and extraction build commands request `worker`. The frozen analysis [executor](../evidence/v2/w001/subjects/r9289/sources/00297:374) uses a0040's analysis tool settings and additionally selects `-C linker-features=-lld` plus explicit host-linker configuration; its comment says this avoids bundled-lld loader trouble without changing Rust functions/cfg. This is a recorded configuration difference and stated purpose, not a proved semantic equivalence of the different compiler pipelines.

Actual344's [cfg probe](/var/tmp/behavior-ir-core036-v2/w001/native-extraction/a0344/commands/cfg/stdout.txt:1) records `feature="worker"`, `debug_assertions`, `overflow_checks`, `panic="unwind"`, GNU/Linux/unix, 64-bit little-endian x86-64 and baseline x87/fxsr/sse/sse2. It also records nightly/compiler-specific cfg such as `ub_checks` and reliable floating-point flags. **There is no matched native329 `--print cfg` receipt among the inspected build records.** More importantly, this probe is run on the user-crate compiler invocation; it does not disclose the cfg/features used to build either distributed standard library. Its absence of `no_global_oom_handling` therefore does not prove the selected branch in precompiled alloc's [`small_probe_read`](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/io/read.rs:869). The std build configuration must be bound separately before source-conditioned allocation/error behavior is claimed.

The two metadata JSONs do agree on the inspected third-party rows: `serde_json 1.0.151` has `default,std,unbounded_depth`; serde/serde_core are 1.0.229 with the same recorded features and shared private registry paths; libc is 0.2.191. Sources are [native329 metadata](/var/tmp/behavior-ir-core036-v2/w001/native-builds/a0329/metadata/stdout.txt) and [actual344 metadata](/var/tmp/behavior-ir-core036-v2/w001/native-extraction/a0344/commands/metadata/stdout.txt). Native metadata's root row has no features while extraction metadata's root row includes `worker`, so those particular metadata snapshots must not be presented as an identical whole build graph; the native **build** command separately enables worker. Cargo metadata does not inventory the implicit core/alloc/std sysroot source or establish their identity.

Confirmed changes are compiler commits/releases, compiler/library artifact identities and recorded linker configuration. Specific I/O body source changes, selected std cfg equality, and observational equivalence remain **unestablished** because the native stable source/configuration side is missing here. No inferred stable version of `write_all`, Take, File or `default_read_to_end` is substituted for unavailable bytes.

## Remaining linkage before a native claim

These are research obligations for prospective work. Keep the existing native compiler and std artifacts unchanged unless an explicit, spec-compatible decision authorizes changing that execution tuple. Switching native329 to the analysis nightly would change the subject and would require its own compatibility/evidence work.

1. Obtain and retain the exact stable 1.98.1 source bytes and first-party commit/component binding through a separately authorized successor. Bind the reached native bodies, dependencies and actual distributed std build cfg; compare them with the analysis source/cfg. The existing missing-output fetch derivation is a useful identity reference, not an executed source acquisition.
2. Bind the exact compiler/default sysroot/library inputs actually used by native329 and actual344, including compiler overrides, precompiled library provenance and any relevant link selection. A recorded install chain, a version probe or equal source hash alone is insufficient to identify every executed body.
3. For matching bodies, establish the source-to-extracted/model semantics under the respective compiler/cfg tuples. For differing bodies or dispatch, prove the required relation for the actual stable implementation or perform separately planned extraction/frontend support against that implementation. Preserve the [previous note's](io-default-model-boundary.md:21) slice/error, cursor/Vec/allocation, actual Take/File/BufWriter dispatch and effect/error-order obligations. Do not promote the larger helper/default into an assumed generic primitive.
4. Retain source/cfg/tool drift controls and then compose the independently checked native instance/runtime relations and complete expected theorem/axiom closure. Actual344 reports `closure_fully_classified=false` and `native_proof=unestablished`; native329 also reports `native_proof=unestablished`. Native329's supplied 77 tests/four binaries/twelve byte comparisons remain conformance evidence. This research creates no new trust/finality assumption and closes no B01–B10, T052, T055 or T059 proof obligation.
