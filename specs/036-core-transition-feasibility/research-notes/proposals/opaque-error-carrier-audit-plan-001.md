## Mathematical boundary

A fresh constant whose sole declaration is `E : Type` supplies a carrier, with no inhabitant, equality law, eliminator, operation, nonemptiness premise, or desired semantic equation. Treating such a fresh signature uniformly is mathematically different from admitting `h : False`, an output equation, or a function with an assumed contract. It does not, by itself, constrain the runtime error domain to be empty, inhabited, finite, singleton, or decidable.

However, this distinction does **not** make the current Lean axiom disappear. A helper that classifies the existing constants has checked a theorem in an explicit external signature. Calling that result “foundation-only,” omitting the carriers from the raw inventory, or reporting it as an unconditional native theorem would be false. The ordinary native audit must continue rejecting it under the current contract.

The stronger uniform statement requires consistent abstraction/substitution through every relevant declaration type and value, including datatypes, constructors, recursors, operations, and theorem dependencies. Its conceptual shape is “for every pair of carrier types, the selected equation holds in the consistently parameterized interpretation.” Merely adding `(JsonError IoError : Type)` to the final theorem does not generalize the original globally fixed carrier constants in `StudyError` or its dependencies. Likewise, choosing definitions for the two names and then checking one instance is not a universal carrier theorem.

The two parameters must remain independent and shared consistently across the reference and view branches and every associated operation. No binder or local premise may assert the target equality, source correspondence, correct first error, or an unproved operation law. A proof of uniformity for this helper still does not prove the external operation interpretation matches Rust; that is an additional source refinement obligation.

## Datatype interpretations and their cost

| Alternative | What is sound | What remains required |
| --- | --- | --- |
| Uniform external type parameters | Arbitrary carriers with full payload fields and no invented operations or laws; strongest abstraction route for this helper | Consistent whole-closure abstraction, source conservation/substitution, fresh proof/kernel checks, and native refinements for actual operations |
| Existing opaque type declarations, explicitly classified | A helper checked relative to the two exact external signature constants; raw axioms disclosed | Separate helper policy and schema; no claim of foundation-only closure or current native acceptance |
| Complete concrete datatype/representation | A definable carrier can remove these particular type axioms | Exact runtime-error representation or a total faithful relation adequate for every admitted use/observable; operations, equality, formatting, causes, and effects as applicable; extraction/source refinement |
| Empty type, `Unit`, success-only error surrogate, or arbitrary convenient `Nat`/bytes model | At most a model instance whose own theorem may be true | Not a justified complete native error interpretation without a proved faithful representation and all required operation relations; empty/singleton substitutions can rule out or collapse real failures |

A wrapper with a constructor carrying an arbitrary payload preserves that payload only if the payload type remains explicit; it does not solve its representation by itself. Conversely, a full concrete error representation could be an appropriate verification-tool extension if source-bound and proved. Nothing in the inspected declarations establishes such a representation, so no particular datatype is recommended as already justified.
