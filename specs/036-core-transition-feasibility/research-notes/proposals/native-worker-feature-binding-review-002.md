## Decision

A new source-bound metadata-only packet can legitimately add evidence about the graph requested for the **unchanged old subject**. The contracts do not say that missing metadata alone invalidates all old development conformance or always requires recompilation. But **the new graph plus the inspected native329 records is not, by itself, an exact effective compile-unit/cfg-to-retained-executable certificate**. Keep that stronger binding unresolved unless authentic old unit/configuration records can close it. Otherwise use prospectively emitted targets with adequate records. Do not relabel native329 as a fresh build or as native proof. Final independent reproduction separately requires rebuilding the selected oracle and workers regardless of this metadata repair. [Correctness, lines 11, 28, 32–40](../../contracts/correctness.md), [reproduction, lines 9–16](../../contracts/reproduction.md).

This distinction qualifies the earlier proposal: “an otherwise correct resolved graph alone is not a fresh compile-unit/source-to-executable relation” is correct; “therefore every documentary supplement forces new executables” does not follow. Changing the *embedded* identity does force a subject change, because the actual Rust function uses `include_str!("../build-identity.json")`.
