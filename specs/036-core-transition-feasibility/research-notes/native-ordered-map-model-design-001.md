## Stored-key preservation and mutable lookup

Lean `TreeMap.insert` replaces the stored comparator-equal key: `getKey?_insert` explicitly returns `some k` when `cmp k a = .eq`. Rust retains the previously stored key on replacement. For String with `LawfulEqCmp`, those key **values** are equal; this can discharge a value-level map model's ordered-entry relation. It does not preserve Rust allocation/address identity or key drop/clone effects. Their exclusion or separate effect model must be explicit in primitive admission. Generalizing this shortcut to arbitrary comparator-equivalent key types would be unsound. [Lean key replacement law](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Std/Data/TreeMap/Lemmas.lean:464), [Rust key retention](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/collections/btree/map.rs:1024).

For an explicitly key-retaining semantic wrapper, choose the existing `getKey?` representative before insertion:

```text
PROPOSED insertOld(m,k,v) : Option V × Map V :=
  let storedKey := (m.getKey? k).getD k
  (m.get? k, m.insert storedKey v)

PROPOSED removeOld(m,k) : Option V × Map V :=
  (m.get? k, m.erase k)

PROPOSED getMut(m,k) : Option (V × (V → Map V)) :=
  match m.get? k with
  | none   => none
  | some v => some (v, fun replacement => m.modify k (fun _ => replacement))
```

These are mathematical interfaces, not claimed generated Aeneas types. The actual extraction may thread an Option/backward continuation differently; write an adapter only after inspecting its exact signature and absence branch. `getMut` absence must not insert a missing entry. The pinned Aeneas Vec precedent returns a value plus backward function: `Vec.index_mut_usize : Vec α → Usize → Result (α × (α → Vec α))`, implemented using `index_usize` and `Vec.set`; its spec identifies both components. That establishes the representation pattern, not a map-specific source theorem. [Vec mutable model/spec](/var/tmp/behavior-ir-core036-v2/w001/analysis-backend/a0054/lean/Aeneas/Std/Alloc/Vec.lean:230).

For the proposed map back function, existing `getElem?_modify` says a comparator-equal lookup becomes `t[k]?.map f`, and every other lookup is unchanged; `contains_modify` and `size_modify` preserve membership/size. Prove: present value is exact; write-back changes that key only; absence/membership and key order remain; writing the original value returns an equivalent map; read-after-write returns the replacement. If key-representative fidelity is required beyond String value equality, choose the stored representative in the modify call too: the existing generic `getKey?_modify` law can return the queried representative. [modify laws](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Std/Data/TreeMap/Lemmas.lean:2555), [modify key law](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Std/Data/TreeMap/Lemmas.lean:2633).

## Ordered forward/backward iteration

`Std.TreeMap.iter` returns a finite `Iter (α × β)` in order; existing `toList_iter` proves `m.iter.toList = m.toList`. `keysIter_toList` and `valuesIter_toList` similarly connect the projected iterators. This file does not supply a Rust-style `next_back` interface. Do not invent `TreeMap.iterRev` or a double-ended theorem. [actual iterator APIs/laws](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Std/Data/TreeMap/Iterator.lean:20).

The smallest explicit Rust iterator model can instead store one **remaining ordered entry list**, initialized to `m.toList`:

```text
PROPOSED IteratorState V := List (String × V)
next []        := (none, [])
next (x :: xs) := (some x, xs)
nextBack xs    := (xs.getLast?, xs.dropLast)
```

This is proposed source-bound model code, not a claim that a native iterator stores a list. Using a single remaining list matters: separate front and reversed-back lists would duplicate entries unless a shared interval/count invariant prevents crossing. Rust Iter's real next and next_back both test and decrement the same remaining `length`; after exhaustion they return None. [native iterator owners](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/collections/btree/map.rs:1734).

Required general iterator laws: `next` decomposes remaining into head plus tail; nonempty `nextBack` decomposes it into prefix plus last; each success removes exactly one endpoint and decreases length by one; None iff empty; exhaustion is fused; any interleaving never repeats or omits an entry; forward-only collection equals `toList` and backward-only collection its reverse. Projected key/value iterators use list map. SDK `List.getLast?`, `dropLast`, `head?_eq_none_iff`, `getLast?_eq_none_iff`, `dropLast_concat_getLast`, `dropLast_concat` and `reverse_reverse` are existing helpers, not yet proofs of this proposed state machine. [List definitions](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Init/Data/List/Basic.lean:321), [dropLast](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Init/Data/List/Basic.lean:1047), [last/empty laws](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Init/Data/List/Lemmas.lean:2956), [last decomposition](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Init/Data/List/Lemmas.lean:3204).

Owning `IntoIter` additionally needs ownership/drop/error treatment; mutable iteration needs the disjoint backward-update construction above. ## Raw map or sorted-list alternative for recursive values

`TreeMap` bundles well-formedness and explicitly warns against use in nested inductive types. `TreeMap.Raw` removes that bundled invariant and is documented for that case. `Raw.WF` is a separate predicate; `Raw.WF.empty`, `.insert [TransCmp cmp]`, `.erase [TransCmp cmp]` and `.modify` establish preservation. `Raw.getElem?_insert`, `.getElem?_erase`, `.mem_toList_iff_getElem?_eq_some` and `.ordered_keys_toList` have the corresponding explicit `h : t.WF` premise. This is a concrete route for recursive JSON object storage; do not place the WF proof back inside a recursive field and assume positivity is solved. Carry it in the external semantic well-formedness/relation and prove operations preserve it. [Raw representation/WF](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Std/Data/TreeMap/Raw/Basic.lean:65), [WF preservation](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Std/Data/TreeMap/Raw/WF.lean:32), [Raw lookup laws](/var/tmp/behavior-ir-core036-v2/w001/analysis-lean-install/a0051/sdk/lean-4.36.0-rc2-linux/src/lean/Std/Data/TreeMap/Raw/Lemmas.lean:235).

A sorted association-list structure wrapping `List (String × V)` with an **external** strict key-order invariant is a second axiom-free option. Define lookup/insert/remove by structural recursion over the list and byte-compatible comparator; retain the old stored pair's key in the equal branch. Ordered insertion/removal and iterator/lens laws then require new list inductions. That is simpler structurally and slower only in the proof model, but creates more proof work than reusing TreeMap laws. It is an independent mathematical model, not an extraction-only alternate Rust implementation. A bundled subtype invariant has the same recursive-positivity concern as bundled TreeMap. Prefer Raw for the eventual recursive backend unless a small list implementation demonstrably reduces integration/proof complexity. These are design inferences from the owning representation restrictions, not compiled findings.
