Research only, 2026-11-19, using the research skill and bounded local primary-source reads. This is one new **unselected** note. No spec, implementation, proof, acceptance, configuration, evidence or private files were changed; no builds, tests, probes, downloads, large IR reads, process inspection, live output reads or protected artifact access occurred. The coordinator supplied the ongoing run; no outcome is inferred. ## Finding

**Core036 does not require a formal proof of every used Rust standard-library implementation's internals. It expressly permits an explicitly justified generic primitive model. It does require a justified relation between that model and the actual source/domain, and it does not authorize arbitrary enlargement of the trusted boundary.** A fully defined independent model can therefore be an engineering route, rather than merely a placeholder awaiting a proof of B-tree balancing or vector allocation internals. Defining it and registering a source name do not, by themselves, complete its admission or a native bridge. This interpretation follows the explicit alternative in T054: “prove linkage to used native implementations **or declared legitimate generic primitives**,” together with correctness construction step 3 and its domain/source-binding requirement. [T052–T055](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/tasks.md:112), [correctness construction](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/contracts/correctness.md:30), [boundary](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/contracts/correctness.md:40).

The exact sufficiency criterion for a *new* primitive justification is not fully specified: these contracts contain no exhaustive primitive allowlist, maximum abstraction size, mandatory proof format for generic-library adequacy, or rule saying registration in Aeneas automatically grants Core036 admission. Thus “every new model must formally verify stdlib internals” adds an unstated universal requirement; “any generic API may now be trusted because Vec is trusted” drops an explicit obligation. The conservative implementation route is to produce a concrete primitive-admission dossier and prospective source/tool/model binding, retain its status honestly, and prove all Core-native consumers/composition. Where the proposed dossier cannot justify the abstraction without assuming a mandatory result, use source refinement or a justified verification-method revision instead. [FR-002/003](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/spec.md:126), [pending external refinements](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/inputs/v2/proof-contract.json:16).

## Prospective `BTreeMap<String,V>` primitive

**Inference from T054 and the pinned API owners:** a reusable finite ordered-map model is a plausible legitimate generic primitive, including when it is newly defined rather than already shipped by Aeneas. It can abstract tree-node layout and balancing while exposing the used API accurately. A bounded search found no BTreeMap/BTreeSet entry in the supplied `ExtractBuiltinLean.ml`; this is therefore a prospective extension, not reuse of an established entry.

The pinned Rust API states that entries and iterators are in key order, strings have lexicographical order, borrowed lookup ordering must match owned-key ordering, and insertion returns the previous value while retaining the stored key on replacement. These are independently specified library properties, not Core036's desired projection/evaluation result. [map API/order](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/collections/btree/map.rs:41), [borrowed lookup](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/collections/btree/map.rs:702), [insertion](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/collections/btree/map.rs:1020).

A concrete admissible proposal needs these separate components:

1. **Defined semantic API.** Represent finite unique String keys with an explicit native-compatible ordering. Define every reached operation: construction, length, lookup/absence, membership, insert/replace/remove, mutable borrow/update and the actual iterator variants. Prove general membership/update/frame laws and complete ordered traversal, including empty maps and newly introduced keys. Keep arbitrary admitted native strings/values and full iterator state, rather than fixture IDs, Nat-only values or a function returning a desired Core result. Bind UTF-8/String/str ordering and borrowing explicitly; no Unicode normalization or unproved Lean-string-order substitution.
2. **Exact extraction binding.** Enumerate actual resolved Rust items, concrete key/value/allocator and borrowed-key instances, trait dictionaries, signatures, forward/backward functions, target/cfg/features and native/analysis versions. Register only those operations. Retain unsupported nodes and reject unmatched instances. A `serde_json::Map` adapter needs its own actual backend/features/operation binding; it cannot be identified with BTreeMap just because both resemble finite maps. T052 requires this source/tool integration independently of proof closure. [T052](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/tasks.md:112).
3. **Justification of the trusted abstraction.** State precisely that the selected library implementation is trusted to realize that generic API at the declared observations, explain why pinned owning documentation/source supports each operation, and identify what is abstracted. Cover allocation/OOM/abort/panic, integer/size limits, destructor/clone/comparator effects where reached, aliasing/mutation and order-sensitive consumers. Restrict a primitive interface to an actual concrete String key domain if useful; do not thereby narrow the feature's admitted input domain. The pinned map warns that unstable key ordering can cause panics/incorrect results/nontermination; generic arbitrary `Ord` cannot silently mean lawful String ordering. [map invariant warning](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/collections/btree/map.rs:53), [FR-003](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/spec.md:128).
4. **Checked consumers and independent controls.** Prove the real selector/projection/view/evaluator/observation algorithms over this API, relating actual full native rows/context/metadata to the model. Bind and check the actual generated consumer bodies, expected root types and allowed axioms. Mutate source key selection, iterator order/omission, map instance/cfg and absence/update behavior and require actual rejection. Tests supplement those general proofs and admission justification; they do not replace either. [B01–B07](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/inputs/v2/native-bridge-contracts-186.json:9), [T059](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/tasks.md:119), [C09](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/contracts/correctness.md:70).

This route need not prove every Rust B-tree balancing step. If the proposal cannot justify erasing a particular implementation effect at Core036's endpoint, that effect must remain in the model or receive a source-bound refinement. A trusted primitive cannot import a premise equivalent to a required bridge; kernel cleanliness alone cannot detect a bad expected theorem or an unjustified source/model association. The proof-contract allowlist remains `propext`, `Classical.choice`, `Quot.sound`; adding a global native-map-correctness axiom would not fit that allowlist. A declared trust item belongs in the justified extraction/model interpretation, visible to source/expected-type review, not hidden as a new Lean axiom or a theorem hypothesis pretending to discharge native linkage. [proof contract](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/inputs/v2/proof-contract.json:94), [full-root requirement](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/contracts/correctness.md:38).

By contrast, declaring `eligibility::finish`, `reference::state_facts`, actual prepared evaluation, or `views::materialize` a “generic map operation” would absorb exactly B01/B02/B04/B05. The source shows why: `finish` checks module/history, request fields, binding count/entity/id and staging; `state_fact_row` interprets native row entities/JSON fields and constructs different Parent/Child projections. Those are feature-specific semantic choices over collections. They require checked actual-source results even if `get`, `insert` and iteration are admitted primitives. [selector](/data/repos/behavior-ir-core-033/experiments/transition-study036/src/eligibility.rs:16), [row projection](/data/repos/behavior-ir-core-033/experiments/transition-study036/src/reference.rs:38), [mandatory bridge prohibition](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/contracts/correctness.md:40).

## I/O: primitive world operations versus library algorithms

Low-level create/read/write/flush/sync operations are plausible runtime/world primitives when they have explicit state, performed effects, partial progress, error and acknowledgement contracts tied to actual implementations. Their being primitive does not mean they always succeed, leave the world unchanged on error, or produce identical answers on two sequential calls. The inspected Aeneas Std I/O file only models `_print` as `ok ()`; that definition supplies no File, BufWriter or successful-delivery relation. [Std/Io.lean](/var/tmp/behavior-ir-core036-v2/w001/analysis-backend/a0054/lean/Aeneas/Std/Std/Io.lean:7), [B08/B09](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/contracts/correctness.md:24).

`Write::write_all` is an actual algorithm over a receiver's `write`: retry Interrupted, advance by the accepted prefix, reject zero progress, propagate the first other error, and succeed only after consuming the buffer. BufWriter overrides it with capacity-sensitive buffering and a cold path that can flush then directly invoke the inner `write_all`; it is not the same default instance. These are source-owned behaviors to preserve, whether implemented through extracted bodies or a source-bound algorithm model. [default loop](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/core/src/io/write.rs:214), [BufWriter override](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/io/buffered/bufwriter.rs:572), [cold path](/var/tmp/behavior-ir-core036-v2/w001/analysis-toolchain/a0039/sysroot/lib/rustlib/src/rust/library/alloc/src/io/buffered/bufwriter.rs:430).

**Inference:** the permitted generic-model alternative does not logically stop at one machine instruction or exclude every generic library algorithm. However, no cited contract automatically admits an entire `write_all`/BufWriter dictionary as a trusted primitive. At this seam the mandatory B successful-delivery requirement explicitly demands the actual wrapper protocol, short writes, flush/extraction/sync failure and partial delivery. A proposal to trust a larger API must still justify its exact dispatch/state/effects contract and show that the Core proof proves those obligations rather than assumes them. The smallest conservative construction remains low-level world primitives plus a source-bound model/refinement of the default/BufWriter algorithms; it avoids silently trusting the very successful-stream property under study. This is a recommended interpretation, not a claim that the contracts supply a formal universal API-granularity rule. [B delivery contract](/data/repos/behavior-ir-core-033/specs/036-core-transition-feasibility/contracts/correctness.md:52).

In the actual wrapper, Counted increments its call counter before inner output and updates byte count after it; Buffered uses 65,536 capacity, extracts on success and error, rejects remaining bytes/panicked writer state, then synchronizes before reporting Delivery. Those source steps remain B08 proof subjects. A Vec model that forgets capacity cannot automatically justify BufWriter's capacity-sensitive scheduling or diagnostics. Equal `Value` arguments alone also do not identify `Counted<W>` and `BufWriter<Counted<W>>` serializer dictionaries. [Counted](/data/repos/behavior-ir-core-033/experiments/transition-study036/src/output.rs:32), [actual output branches](/data/repos/behavior-ir-core-033/experiments/transition-study036/src/output.rs:68). The prior [I/O default note](io-default-model-boundary.md) records the concrete algorithm obligations; its claim that transparency/hash alone is insufficient stands. Its proposed source-refinement route should not be generalized into an unstated requirement to formally prove every legitimately admitted generic stdlib primitive.

## Actionable boundary decision

Proceed with a prospectively specified, fully defined `BTreeMap<String,V>` API model and exact source-instance mapping **as a candidate generic primitive**, with checked API laws and an explicit source/domain/TCB justification dossier. Keep its admission/refinement status separate from representability, kernel success and B01–B10. This is work permitted by T052/T054; it is not an approval to mark any dependency proved. Compare the proposal against the Vec/Array pattern without claiming that pattern formally verifies Rust stdlib.

The remaining decision is precise: does the independently reviewed dossier justify trusting the selected library API at Core036's full error/effect/observation scope, or does it leave a semantic refinement unresolved? If unresolved, retain that mandatory work and implement source-bound refinement, a real shared Rust refactor with compatibility proof, or a justified prospective method revision under correctness step 4. No acceptance change is needed merely to explore this existing permitted alternative; no inference from the word “generic” can settle admission. All exact native relations, source/compiler binding, checked consumer/adapters, expected roots, negative controls and fresh full closure remain required. No native completion is claimed by this note.
