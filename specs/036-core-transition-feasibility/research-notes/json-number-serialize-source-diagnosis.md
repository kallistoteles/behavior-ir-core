## Finding

The concrete metadata gap is the **outer `serde_json::number::Number` type**, not private enum N. In unchanged actual342 raw LLBC, Number is type def55 with `kind: Opaque`; N is type def232 with `kind: Enum` and all three variants. Accessing `self.n` can therefore require symbolic expansion of opaque Number before matching N. The exact original exception/backtrace remains unretained, but the source contains a direct mechanism connecting this gap to the generic error. There is no established float cause or need for a compiler patch.

Actual342 imported the LLBC and reported exactly `Unexpected error` at the entire Number match, followed by a warning from `interp/Interp.ml:686`. It then emitted partial output. The retained translation command exited 1; stderr is empty ([stdout](/var/tmp/behavior-ir-core036-v2/w001/native-extraction/a0342/commands/translate/stdout.txt:1), [command/result](/var/tmp/behavior-ir-core036-v2/w001/native-extraction/a0342/commands/translate/result.json:1)). `Interp.ml:686` is the **catch/report** site: it catches a `CFailure`, prints a warning using the original `error.span`, and returns an `Error` node using `error.msg`. It is not the origin of that message ([catch](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/Interp.ml:669)).

## Actual type dependency and confirmed raw metadata

In pinned serde_json 1.0.151, `Number` contains `n: N`. With `arbitrary_precision` disabled, private `N` is a three-variant enum deriving Copy/Clone: `PosInt(u64)`, `NegInt(i64)`, and `Float(f64)` ([definitions](/var/tmp/behavior-ir-core036-v2/w001/cargo/registry/src/index.crates.io-1949cf8c6b5b557f/serde_json-1.0.151/src/number.rs:20)). The extracted source span selects the non-arbitrary-precision `Serialize` implementation. Its complete operation is `match self.n`, dispatching to serializer `serialize_u64`, `serialize_i64`, or `serialize_f64` ([body](/var/tmp/behavior-ir-core036-v2/w001/cargo/registry/src/index.crates.io-1949cf8c6b5b557f/serde_json-1.0.151/src/number.rs:372)).

The raw LLBC options include the exact Value/Number Serialize implementation methods, but no explicit Number type source-support pattern. The bounded post-closure audit of `translated.type_decls` found:

| Exact name | Type def_id | item_meta.opacity | kind |
| --- | --- | --- | --- |
| `serde_json::number::Number` | 55 | `Foreign` | `Opaque` |
| `serde_json::number::N` | 232 | `Foreign` | `Enum`: PosInt, NegInt, Float |

These observations come from the unchanged [actual342 LLBC](/var/tmp/behavior-ir-core036-v2/w001/native-extraction/a0342/worker_entrypoints_names.llbc:1). The generated files independently corroborate them: the external template emits Number as a type axiom, whereas Types emits N as an inductive with U64/I64/F64 payloads ([Number axiom](/var/tmp/behavior-ir-core036-v2/w001/native-extraction/a0342/generated/TypesExternal_Template.lean:245), [N enum](/var/tmp/behavior-ir-core036-v2/w001/native-extraction/a0342/generated/Types.lean:1092)). The `Foreign` label alone does not determine whether the representation is available; the declaration's `kind` does. N-opacity is falsified by this audit. The raw opaque Number declaration has no `n` field representation to follow; the source establishes that field dependency.

The interpreter's `SwitchDiscriminant` path reads the place, strips shared loans, and, for a symbolic value, calls `expand_symbolic_adt`. That calls `compute_expanded_symbolic_adt_value`; for a user ADT it retrieves the declaration and calls `Substitute.type_decl_get_instantiated_variants_fields_types` before creating a fresh symbolic value for each field and evaluating branches ([switch](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/InterpStatements.ml:992), [expansion](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/InterpExpansion.ml:607), [field instantiation](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/InterpExpansion.ml:278)). The earlier projection path is especially relevant: `project_value` returns `FailSymbolic` when projecting through a symbolic value, and read-place handling responds with `expand_symbolic_value_no_branching`. Struct expansion to access `Number.n` therefore reaches the same field-instantiation machinery before an N discriminant can be read ([projection](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/InterpPaths.ml:166), [read-place expansion](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/InterpPaths.ml:449)). The emitted span alone does not identify that intermediate declaration.

## Where the generic message can originate

The exact lossy wrapper is in Aeneas `llbc/Substitute.ml:234–242`. Normally it catches **any OCaml `Failure`** from Charon's variant-field instantiation and replaces the original message with `[%craise] span "Unexpected error"`. With `Config.fail_hard` enabled it calls the underlying function directly ([wrapper](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/llbc/Substitute.ml:234)).

The underlying pinned Charon function handles Enum, Struct, and Union declarations. For **Alias, Opaque, or TDeclError** it explicitly raises `Failure ("Can't retrieve the variants of non-adt type: " ^ show_name def.item_meta.name)`. This is a precise source-level route from the confirmed opaque Number dependency to the actual generic error. The wrapper also covers other `Failure` exceptions during substitution, so its presence alone does not prove which declaration or condition failed ([Charon implementation](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/charon/charon-ml/src/Substitute.ml:379)).

A separate exact-message path exists in `InterpAbs.convert_value_to_abstractions`: when avalues are nonempty it unwraps required output/input continuation expressions with `"Unexpected error"`. Either absent option raises through `Errors.unwrap_with_span`. Thus a missing continuation is an alternative source-level explanation until the original emitter/backtrace is retained ([continuation unwraps](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/InterpAbs.ml:49), [unwrap behavior](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/Errors.ml:213)).

The match source span, confirmed opaque Number, and direct ADT-expansion path make Number expansion the leading explanation. It does not eliminate the alternative. The current log's default formatting suppresses the original emitter location: `Errors.push_error` adds that location only when `print_error_emitters` is enabled ([error formatting](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/Errors.ml:90)).

## Copy and float boundaries

This match performs no float arithmetic in its Rust body. The float branch passes its payload to a generic serializer method. Aeneas `copy_value` handles literals uniformly, refreshes borrow-free symbolic copies without a float-specific branch, and calls `ty_is_copyable`; in this pinned source that predicate returns true, trusting rustc's typechecking. Primitive constant conversion also includes CFloat/VFloat ([copy](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/interp/InterpExpressions.ml:149), [copyability](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/llbc/TypesUtils.ml:238), [float constants](/var/tmp/behavior-ir-core036-v2/w001/tmp/nonpos-source/a0273/aeneas/src/llbc/TypesUtils.ml:5)). These observations weaken an unsupported “f64 cannot be copied” explanation; they do **not** establish end-to-end f64 translation or serializer adequacy. A float-specific correction is premature.
