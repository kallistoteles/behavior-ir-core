## Exact provider boundary

| Requested stage | Local definition provider | External non-const function |
| --- | --- | --- |
| `--mir=built` | `tcx.mir_built(LocalDefId)` | `tcx.optimized_mir(DefId)` when available |
| `--mir=promoted` | `tcx.mir_promoted(LocalDefId).0` | Same optimized metadata body |
| `--mir=elaborated` | `tcx.mir_drops_elaborated_and_const_checked(LocalDefId)` | Same optimized metadata body |
| `--mir=optimized` | `tcx.optimized_mir(DefId)` | Same optimized metadata body |

Charon checks `as_local()` before querying any early stage, clones an unstolen local body, and falls back to optimized MIR if the early body was stolen. For foreign definitions it queries MIR availability and uses optimized MIR for function bodies. Its CTFE fallback covers eligible constants/statics/const functions; it cannot furnish the non-const `write_all` body. Monomorphization/substitution happens **after** this retrieval and cannot recover an earlier stage. [Owning implementation](https://github.com/AeneasVerif/charon/blob/454586e9b770231e66d2062993e632dfc06463e2/charon/src/bin/charon-driver/translate/get_mir.rs#L36)

The CLI default is `promoted`; `--precise-drops` raises it to at least `elaborated`. The enum describes built as post-lowering, promoted as borrow-checker MIR, elaborated as post-drop elaboration, and optimized as post-optimization. Thus an unspecified `--mir` already requests the relevant early local stage. [CLI and levels](https://github.com/AeneasVerif/charon/blob/454586e9b770231e66d2062993e632dfc06463e2/charon/src/options.rs#L397), [default selection](https://github.com/AeneasVerif/charon/blob/454586e9b770231e66d2062993e632dfc06463e2/charon/src/options.rs#L875)

Rust independently enforces this boundary: built, promoted and elaborated queries take `LocalDefId`; optimized and CTFE queries accept `DefId` and have external providers. [Rust query declarations](https://github.com/rust-lang/rust/blob/923c95cdf5ba65cea505aa2ea829f578e1506ed8/compiler/rustc_middle/src/queries.rs#L644) The metadata encoder selects generic/cross-crate-inlineable reachable functions, or all functions with `always_encode_mir`, and serializes the **result of `optimized_mir`**. CTFE has a separate table. The decoder's external providers read those tables; there is no serialized early-function-body stage for Charon to select. [Encoder policy](https://github.com/rust-lang/rust/blob/923c95cdf5ba65cea505aa2ea829f578e1506ed8/compiler/rustc_metadata/src/rmeta/encoder.rs#L1091), [encoded bodies](https://github.com/rust-lang/rust/blob/923c95cdf5ba65cea505aa2ea829f578e1506ed8/compiler/rustc_metadata/src/rmeta/encoder.rs#L1825), [external table providers](https://github.com/rust-lang/rust/blob/923c95cdf5ba65cea505aa2ea829f578e1506ed8/compiler/rustc_metadata/src/rmeta/decoder/cstore_impl.rs#L248)

## What existing options can and cannot change

Charon's driver sets `always_encode_mir=true`, `mir_opt_level=0`, `mir_preserve_ub=true`, and disables CheckAlignment/CheckNull passes. It applies this setup when compiling dependencies as well as selected crates. Consequently a dependency **newly compiled through that driver** can supply less-optimized runtime MIR downstream, though its foreign body still comes through the optimized query. A dependency selected as the current crate can instead use local early-stage queries. Neither case changes already-built standard-library metadata. [Driver configuration and callbacks](https://github.com/AeneasVerif/charon/blob/454586e9b770231e66d2062993e632dfc06463e2/charon/src/bin/charon-driver/driver.rs#L30)

`--sysroot` can choose other metadata; the default mechanism may build a Miri sysroot with `always_encode_mir`. That increases body availability, not the number of historical MIR stages encoded. Switching sysroots or rebuilding std is outside this question's fixed-stdlib/no-rebuild conditions and would require a separately bound subject. [Sysroot implementation](https://github.com/AeneasVerif/charon/blob/454586e9b770231e66d2062993e632dfc06463e2/charon/src/bin/charon/toolchain.rs#L144)

**Actionable argv conclusion:** do not spend the next actual attempt merely appending `--mir=built`, `--mir=promoted`, or `--mir=elaborated` as a fix for this external body. All take the same foreign branch. `--rustc-arg=-Zmir-opt-level=0` is already redundant with the driver and cannot rewrite loaded metadata. There is no qualifying argv modification to recommend under the stated constraints. A local wrapper, inclusion rule, default-method duplication or substitution does not make the original foreign definition local. This conclusion follows from the provider and driver above; no command was run to test it.

Source alone does not identify the exact historical pass that produced the supplied body, but no such attribution is needed for the metadata limitation. ## Principled existing Aeneas boundary

The narrow API boundary is **`SliceIndex<RangeFrom<usize>, [T], [T]>::index`**, reached through slice `Index::index`. Aeneas already registers that exact Rust name to `core.slice.index.SliceIndexRangeFromUsizeSlice.index`, plus its trait instance. This is an existing generic slice model, not an opaque whole-Core or whole-`write_all` equivalence. [Generated function mapping](https://github.com/AeneasVerif/aeneas/blob/1dc8ad31b1b062a77c50e29144a6c7bba955fa09/src/extract/ExtractBuiltinLean.ml#L1196), [trait-instance mapping](https://github.com/AeneasVerif/aeneas/blob/1dc8ad31b1b062a77c50e29144a6c7bba955fa09/src/extract/ExtractBuiltinLean.ml#L1827)

There are material limits. The checked model returns `s.drop r.start` when in bounds but currently returns `.undef` when out of bounds; its step specification assumes `r.start ≤ s.length`. Both unchecked raw-pointer entries explicitly lack a model and always return `.undef`. The actual Rust checked API **panics** on an excessive start. Therefore existing registration is not evidence of complete checked-API correspondence, and arbitrary `Write` implementations must not silently acquire an assumed `n ≤ buf.len()` law. Either establish the bound for the actual admitted implementations through source-bound reasoning, or repair/model the exceptional branch while preserving the declared observations. [Model and unchecked placeholders](https://github.com/AeneasVerif/aeneas/blob/1dc8ad31b1b062a77c50e29144a6c7bba955fa09/backends/lean/Aeneas/Std/Slice.lean#L655), [bounded specification](https://github.com/AeneasVerif/aeneas/blob/1dc8ad31b1b062a77c50e29144a6c7bba955fa09/backends/lean/Aeneas/Std/Slice.lean#L1006)

For this boundary to help the supplied failing body, the API call must survive extraction, or a new source-directed frontend normalization must soundly identify the already-inlined checked-suffix computation and map it to that API model. Merely marking the slice API opaque cannot recreate a call absent from the MIR. Charon's existing `--index-to-function-calls` pass transforms AST `Index`/`Subslice` projections after extraction/control-flow reconstruction; it has no rule reconstructing this inlined checked-suffix computation from the pointer sequence. [Projection transformation](https://github.com/AeneasVerif/charon/blob/454586e9b770231e66d2062993e632dfc06463e2/charon/src/transform/simplify_output/builtins_to_function_calls.rs#L196), [pass ordering](https://github.com/AeneasVerif/charon/blob/454586e9b770231e66d2062993e632dfc06463e2/charon/src/transform/mod.rs#L224)

Any later integration must bind the exact Rust source/compiler/stdlib metadata, target/cfg, Charon/Aeneas revisions and actual dispatch; retain the default's empty/zero/short-write/Interrupted/other-error order and actual receiver effects; and preserve suffix bounds, panic behavior, element order and borrow semantics. Keep actual overrides intact. Do not copy the loop into an alternate proof-only algorithm or patch emitted LLBC. A source-directed mapping/refinement and rejection on source/shape drift remain required work, not consequences of an existing builtin name.
