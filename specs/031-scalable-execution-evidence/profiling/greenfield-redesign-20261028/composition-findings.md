# Composing incremental execution, authenticated evidence and accumulated history proofs

Research date: 2026-10-28. Core source identity: `fc73fa36b959aeaf54cff2f38dd190c4389c3fa1`. This is a source review and a proposed composition contract, not an implemented redesign or an end-to-end proof. No dependencies were installed, proof artifacts built, benchmarks reproduced, or production code changed. External mechanization statements below are author reports and source inspection, not independent kernel checking or an axiom audit. Older reports remain unchanged.

The measured [single-create profile](../single-create-20261028/report.md) supplies the motivation: 4,085,191 record bytes at 8,192 parents, approximately 79% repeated constraint traces, with median evaluate/commit times of 277/1,658 ms. Those measurements establish neither a speedup nor a proof-system cost for a redesigned implementation.

## 1. The two options address different growth dimensions

**A: typed incremental Core execution plus shared/authenticated evidence.** A deep typed evaluator can reuse decoded values, share evidence nodes, and maintain query results or constraint summaries after a delta. This can target repeated current-step work and repeated bytes. It does not by itself replace the logical obligation to establish every preceding transition from a trusted start. A fresh verifier must still obtain and check the requisite chain/evidence, or accept an explicitly trusted checkpoint. Sharing reduces duplicate support; it does not give an inductive proof that an arbitrary new history is valid. A full legacy trace export remains proportional to the bytes requested, even if its backing representation shares nodes.

**B: accumulated history proof.** Nova proves repeated applications of a specified computation, including nondeterministic computation with witnesses. Its paper states prover work per step proportional to the step computation size; independence from the number of preceding steps is not independence from the amount of work encoded in a step. A full-state interpreter or scan inside that relation still requires its full-state work. [Nova paper](https://eprint.iacr.org/2021/370), abstract and construction; [implementation overview](https://github.com/microsoft/Nova).

**Composition inference.** A can reduce the work that B must prove, while B can prevent a cold verifier from rechecking an unbounded prefix. Their benefits multiply only after proving that A's smaller transition/checker relation has the required Core semantics. Attaching an IVC proof to A's output without this relationship proves only the relation actually encoded.

## 2. Authentikit is strong evidence for a narrower theorem

The [CCS 2025 paper](https://iris-project.org/pdfs/2025-ccs-veriauth.pdf), §§2.2, 4–7, reports Rocq/Iris proofs for a System-F-like language with references. Security relates accepted verifier output to ideal execution on collision-free traces. Correctness relates honest prover, verifier and ideal output. It covers proof buffering, deserialized-value caching, a heap cache, and a manually proved Merkle retrieval linked to generated operations. Faithfulness of the model to compiled OCaml is explicitly trusted; the theorem is not a verified OCaml compiler or a Core semantics theorem. The performance implementation additionally changes serialization/file-stream details (§8), so measured executable performance must not be described as wholly covered by the formal model.

An independent source fetch in this review resolved `jtassarotti/veri-auth` to commit `24c41ec37e5f12f75a40b00c65b787dea63810b0`. A particularly important scope limit is visible in the [basic stateful verifier](https://github.com/jtassarotti/veri-auth/blob/24c41ec37e5f12f75a40b00c65b787dea63810b0/src/basic/verifier_buf_magic_state.ml#L63): `run` clears the cache before executing. Its authenticated read first checks a supplied serialization against its hash and deserializes it; subsequent reads reuse the validated value. Therefore the artifact directly illustrates reuse within a computation/batch, **not** a persistent verifier cache safely inherited across arbitrary independent histories, module upgrades or process recovery. The file was fetched directly, 1,663 bytes, SHA-256 `b09a25082a798f0e421a9c6524256df9d8ba151d935bf4c400b4410573da83bc`.

The [formal implementation](https://github.com/jtassarotti/veri-auth/blob/24c41ec37e5f12f75a40b00c65b787dea63810b0/theories/examples/authentikit_buf_magic_state.v#L46) allocates an empty table when constructing the verifier interface. The [security proof](https://github.com/jtassarotti/veri-auth/blob/24c41ec37e5f12f75a40b00c65b787dea63810b0/theories/examples/authentikit_buf_magic_state_security.v#L27) maintains a cache invariant: each stored value has a valid typed serialization whose hash is its key. Its `authentikit_security_syntactic` theorem requires a suitably polymorphic, well-typed client and equality-observable result type. The [correctness theorem](https://github.com/jtassarotti/veri-auth/blob/24c41ec37e5f12f75a40b00c65b787dea63810b0/theories/examples/authentikit_buf_magic_state_correctness.v#L456) relates the prover's produced proof to verifier acceptance and ideal execution under the formal collision-aware adequacy judgment. These declarations were read, not executed.

**Core inference.** Reusing authenticated bytes/typed values is a different claim from reusing a prior semantic result. A constraint certificate additionally depends on the module, bindings, exact applicable policy/context, evaluation semantics and all relevant state dependencies. Persistent reuse requires a new invariant/lifecycle argument; it must not be presented as already established by Authentikit. A cache local to an independent verifier can be trusted after that verifier validates its entries; a token made by the untrusted producer cannot stand in for that validation.

## 3. Existing primary precedents for the hybrid

[Pantry, “Verifying computations with state”](https://www.pepper-project.org/pantry-sosp13.pdf), §§3, 5.1, composes proof-based computation with content-addressed storage. Its RAM load constraints check a witness path against an input digest; stores check continuity from that digest and output the updated digest. The verifier must bootstrap the initial digest, for example by constructing initial state locally. This is a concrete precedent for binding authenticated memory inside a computation proof. It is a published construction and built system, not a machine-checked correctness proof of its compiler or Core. The paper explicitly separates verifying execution from verifying that the program itself expresses the intended behavior.

[Nebula](https://eprint.iacr.org/2024/1605), revised 2026-05-18 and listed as IEEE S&P 2026, introduces commitment-carrying IVC, read-write-memory arguments, and a switchboard for avoiding costs of unused instructions. This changes how efficiently the selected relation can be proved. RAM consistency and indexed lookups do not automatically establish arbitrary-query completeness or Core's meaning. Initial memory still needs to be bound to an accepted genesis/state representation; proving consistent reads from adversarially selected initial memory proves the wrong computation faithfully.

[Proof-Carrying Data](https://projects.csail.mit.edu/pcd/) is the relevant primary model for data whose provenance is a recursively checked computation DAG. Its 2010 construction is in a signature-card model, so it is not a turnkey transparent software protocol. [“Enforcing Language Semantics Using Proof-Carrying Data”](https://people.seas.harvard.edu/~chong/abstracts/ChongTV2013.html) explicitly connects well-traced values to a specified language/runtime semantics. These support an architectural direction, not a claim that an existing proof-carrying materialized-view library proves Core. No such library or Core-specific theorem was established in this review.

**Proposed materialization discipline.** A materialization can carry a proof that it equals an explicitly defined query/summary of a particular authoritative state. Its updates then carry proofs preserving that relation. Hashing the view, or proving only that the update code ran, is insufficient if initial contents or the update rule are wrong. Pure runtime caches need not all be persisted or committed: they can be derived/rechecked and discarded. A cache used as a cryptographic premise must be reconstructed within the relation or authenticated against a commitment whose semantic correctness is already established.

## 4. A concrete conditional composition contract

Everything in this section is a proposed obligation for the greenfield design. It is not a theorem imported from any cited project.

Let the public accumulator state `Z_i` bind, using unambiguous versioned encodings:

- lineage/genesis identity; exact history position and record identifier; canonical content-state identity;
- current schema, admitted behavior/module identity, semantic/evidence profile, complete policy identity and circuit/checker identity;
- authenticated authoritative-state root(s), and any index/summary roots used as premises;
- commitment to the normative event/output stream, including ordered command occurrences.

The current `HistoryRef` explicitly contains `format`, `store`, `state`, `position`, and `record`: [local definition](../../../../crates/behavior-store/src/documents.rs). Equal MuHash3072 state identity must not identify equal histories. An auxiliary Merkle/RAM root needs a checked common representation with that state identity; asserting that the two roots “refer to the same state” is the missing obligation, not its discharge. If a new contract replaces MuHash3072 or event encoding, it needs explicit versioning and a correspondence/adoption rule.

Define a step relation `R_Core(Z_i, event_i, Obs_i, Z_(i+1); witness_i)` with at least the following checks:

1. **Subject and authority.** Bind exact parent, module/schema/profile, full applicable policy set, request/bindings/input and trusted context. Check admission or bind a separately verified admission certificate. Authentication of a policy document alone does not establish that the complete policy set was selected or authorized.
2. **State access and update.** Every supplied read/write is consistent with authoritative memory, ordered step semantics and before/after state. Check creates, removals, permanent identities and reference integrity. Check simultaneous effects according to Core's rule, not an arbitrary sequential rewrite. Bind unchanged memory correctly through the update mechanism.
3. **Coverage.** Establish the full set of semantic obligations. Include positive reads, absence facts, query membership and nonmembership/range boundaries, incoming-reference absence, all affected constraints, and dependencies of derived computations. A purported list of “all dependencies” is not self-authenticating. In particular a new row entering an empty query must invalidate/recheck the result even though no old result member changed. RAM consistency alone says nothing about whether an omitted address should have been queried.
4. **Summary invariant.** For every index/aggregate/cached result used to skip work, prove or derive its meaning over the authoritative state; preserve it under every affected delta. The induction base must establish the complete initial index/summary. An update law cannot repair an unproved initial count, reverse-reference index or query result. Unknown dependencies are affected unless a sound fallback establishes coverage.
5. **Semantic result.** Check arithmetic definedness, overflow, laziness, branch/capture behavior, rule order, allowed/denied outcome, effects and selected semantic errors. An algebraic summary is inadequate where changed evaluation order changes which error appears. Bind ordered command intents with occurrence identity and multiplicity; repeated equal commands must remain distinct occurrences. If normative traces are compacted, provide exact expansion or a deliberately versioned semantic interpretation with correspondence to the reference observation.
6. **Event/history update.** Construct the exact next event from the checked outcome and inputs, including original committed time/context and commands; derive the next record/history commitment and state root. Do not merely verify inclusion of separately supplied hashes in an evidence object. A command-only event can change exact history without changing state.
7. **Boundary rules.** Verify initialization/adoption, module changes and schema migrations with explicit transition rules. Bind source and target meanings and the appropriate new checker/circuit identity. A proof for one module/circuit does not authorize interpreting the same roots using a new one.

A sufficient theorem shape is:

```text
InitSound(Z_0)
and IVC-Soundness(vk, R_Core)
and VerifyIVC(vk, Z_0, n, Z_n, proof)
and CheckerRefinesCore(R_Core, exact_semantics_and_observations)
and Encoding/commitment binding assumptions
  imply existence of a Core-valid n-event history with these exact endpoints
          and the bound normative event/output stream.
```

The theorem is **conditional** until each displayed premise is proved/discharged. A trusted checkpoint gives a theorem from that checkpoint, not from genesis. A proof-only `SafetyModel` or invariant predicate can support the correspondence theorem at build time; it must not become hidden runtime business state. Runtime auxiliary data must have an explicit reconstruction/checking contract.

## 5. Full interpreter versus semantic witness checker

**Full interpreter route.** Encode/prove execution of a specified interpreter or VM whose behavior has been related to Core. This gives broad coverage, but only if parsing/admission, policies, data access, effects and observation serialization are all covered or pinned by checked inputs. If the interpreter traverses every entity, proving it preserves that cost. A proof of a native binary faithfully running is not automatically a proof that the binary implements the intended semantics.

**Small checker route.** The fast native executor emits a semantic witness; a simpler checker verifies `R_Core`. The independent verifier trusts the public checker/relation and proof verification, not the producer's Rust process. However, checker soundness is substantive: acceptance must imply an actual Core transition with complete coverage and the required observations. Proving only Merkle paths, arithmetic operations or a final delta does not establish it. Completeness matters operationally too: an honest supported execution must admit an acceptable witness, or the design needs a stated unsupported/fallback behavior.

**Authentikit plus independent IVC.** Running a verified authenticated-data verifier beside an IVC verifier can be sound if their public subjects are bound and their theorems compose. It does not suffice that both mention an evidence root. The IVC relation must consume authenticated values according to the semantic contract, or verify the authenticated-checker computation, or rely on a separately verified checker result that the independent consumer actually checks. A producer-generated `Checked<T>` label is not a cryptographic premise. A sufficient complete proof relation can remove the need to trust producer execution; the trust moves to proof soundness, the relation/checker correspondence, encodings and the independent verifier implementation.

## 6. Validity, proof status, availability and publication remain separate

**Proposed status model.** Keep semantic outcome (`ALLOW`, `DENY`, a specific semantic error/refusal) separate from evidence status (`locally checked`, `proof pending`, `proof verified through exact position k`, `proof invalid`, `unsupported`, `unavailable`). A valid proof of a denial is not permission to commit an allowed transition. A pending/failed proof is not evidence that the business transition was invalid. If proving is asynchronous, an externally certified prefix ending at `k` must never be displayed as certifying an unproved suffix ending at `n`. The acceptance policy for publishing or executing effects before proof completion is an explicit product/trust decision.

**Availability/replay inference.** A succinct proof can establish a committed computation without transferring the state, event log, traces, module or witnesses needed to continue computation, answer a new query or replay/export history. Define retention, export, fetching, pruning, missing-object handling and reconstruction separately. Hashes and proof verification do not manufacture omitted bytes. A proof-verifiable endpoint can remain valid while a requested historical export is unavailable; report those findings distinctly. If full replay remains part of the contract, retain sufficient data even when routine validity checking no longer replays it.

**Publication/recovery inference.** Write and validate the required object graph before atomically publishing the head under an exact-parent compare-and-swap rule, with backend durability semantics stated. Concurrent rejected candidates must not contaminate canonical summaries or proof state. Asynchronous proof sidecars bind the exact event/head and may be published later without changing the event. These storage facts are separate from an algebraic transition proof. For persisted-before-lost-ack recovery, resolve the original event and its exact committed time/context/command occurrences before retrying; a matching final state cannot distinguish “not committed” from “committed command-only event.” A fresh request with new context must not inherit the original event's authority. Core's original-event behavior is documented in [existing recovery evidence](../../evidence/source-map.md) and exercised by local recovery tests; this note does not rerun them or establish general crash safety. Physical exactly-once command delivery additionally requires the host's durable occurrence/deduplication protocol.

## 7. Disposition

The strongest supported direction is a **conditional hybrid**: a typed incremental executor, explicit authenticated/derived materializations, a small semantic checker with a proved Core correspondence, and IVC over exact state/history/output bindings. Authentikit supplies a valuable model for safe evidence reuse; Pantry supplies a concrete memory/proof composition pattern; Nova/Nebula supply accumulation and memory machinery. None supplies the complete `R_Core` theorem. Persistent cross-run caches, initial summary validity, complete query/reference dependencies, code-to-relation correspondence, availability and original-event publication/recovery remain separate obligations and measurement targets.
