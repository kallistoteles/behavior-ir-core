# Greenfield Core: IVC, authenticated memory, and an incremental semantic checker

**Research date:** 2026-10-28. **Core source:** `fc73fa36b959aeaf54cff2f38dd190c4389c3fa1`. This is a design investigation, not an implementation or dependency recommendation. External papers, documentation and selected source were inspected; no external proof was built, independently replayed, audited or benchmarked here. No machine-checked theorem about Core follows from these sources.

## Main finding

Nova is a serious option for making an independently checked history certificate stop growing with the length of history. It does not, by itself, make proving one Core transaction proportional to its changes. A promising composition is **native incremental execution plus an independently sound semantic-witness checker, with IVC proving successive executions of that checker**. Whether that composition is cheaper than proving the existing evaluator is an experimental question. Its hardest missing part is proving the checker's complete coverage of Core semantics, rather than merely showing that supplied data has authentic hashes.

The [measured first-create baseline](../single-create-20261028/report.md) remains relevant: 4,085,191 decision bytes at 8,192 existing entities, 79% trace, evaluate median 277 ms and commit median 1,658 ms. Most measured work is representation, validation and hashing. A greenfield evidence contract can remove expanded trace transfer from ordinary verification; maintaining byte-identical old decision hashes still requires accounting for those bytes somewhere. Native typed execution and IVC target different parts of this cost.

## Fixed circuits, variable transactions, and dynamic modules

The pinned [`StepCircuit` interface](https://github.com/microsoft/Nova/blob/01b1e2d662a847ed7029770ecbaf6687398899dd/src/traits/circuit.rs) has a fixed state arity and synthesizes the step relation. The pinned [`PublicParams` and IVC implementation](https://github.com/microsoft/Nova/blob/01b1e2d662a847ed7029770ecbaf6687398899dd/src/nova/mod.rs) stores circuit shapes established during setup. Updating private witness values is different from changing the supported constraint graph. Circuit shape must not accidentally depend on secret data or Rust branching during witness generation.

For Core, there are three concrete routes:

1. **Universal Core interpreter.** Authenticate admitted IR as input and prove small interpreter steps. Instructions, program counter, typed values, frames, lazy branches, checked arithmetic and pending obligations become explicit machine state. Module switches can be data transitions under a fixed interpreter relation, provided admission/authority and old-to-new semantics are also checked. Variable work uses more microsteps; it need not pad every transaction to the largest store.
2. **Compiled module/action circuits.** Translate admitted Core to specialized circuits and authenticate the mapping from exact admitted module/profile to the circuit/verifier key. Supported bounds or chunking must be explicit for loops, queries and variable state. This may remove interpreter overhead, but creates a new compiler-correctness obligation. A predefined non-uniform family can select among compiled relations; it does not itself justify arbitrary circuit replacement at runtime.
3. **Compiled guest on a zkVM.** Compile a deterministic evaluator or semantic-witness checker to a supported ISA. This reduces handwritten circuit semantics, at the price of proving guest instructions and relying on compiler/VM/library correctness and supported system calls. It does not eliminate the checker-to-Core equivalence question or authenticate host-supplied database answers automatically.

An IVC step should have an explicit transaction boundary marker. A proof of 10,000 interpreter steps does not imply 10,000 commits. A step budget exhaustion or truncated transaction must not publish a valid committed head. Chunking also needs stable request/context binding, so a producer cannot change its request halfway through a transaction.

## Cost variables that must stay separate

Let `N` be live-state size, `T` semantic transactions, `h_j` proof microsteps for transaction `j`, `s` a fixed microstep constraint shape, `a_j` authenticated accesses, `d_j` changed entities, `B_j` bytes required by a requested full audit export, and `p` externally processed public input/output bytes. These are design variables, not measured Core proof costs.

| Work | Relevant dependence | What IVC can and cannot remove |
|---|---|---|
| Native evaluation and witness production | Input parsing, actual semantic work, dependencies and data access | Typed reuse can remove duplicate parsing/copies even if the circuit is unchanged. |
| Folding | Roughly a sum over actual microsteps and their relation sizes; uniform Nova pays for its fixed relation at each fold | Prior history length does not require re-proving every earlier step, but `sum(h_j)` still represents producer work. A full-state scan still takes full-state work. |
| Uncompressed recursive proof verification | Step shape/witness checking and public state, not number of prior folds | Current code checks accumulated R1CS satisfiability. History-independent is not circuit-size-independent. |
| Compression/publication | Compressor and step shape; publication frequency | Compressing every transaction can dominate latency even when folding is incremental. Periodic compression changes freshness, not what pending heads prove. |
| Compressed verification | Chosen scheme, step shape, security parameter, public claim size | MicroNova gives the explicit logarithmic bound above. Avoid reading README “does not depend on circuit size” as eliminating all logarithmic work. |
| Authenticated state | Depends on memory/index scheme and complete semantic accesses | For a balanced Merkle design, `a_j` accesses plausibly need logarithmic paths in address-space capacity, with constants determined by hashing and batching. This is a proposed model, not a measured Nova result. |
| Audit extraction and availability | At least requested output/data bytes | A small proof does not construct a large public document, retain its preimages or furnish missing data. |

The first two code observations in this table are supported by the pinned [IVC source](https://github.com/microsoft/Nova/blob/01b1e2d662a847ed7029770ecbaf6687398899dd/src/nova/mod.rs). It binds parameter digest, step count and initial/final recursive state; Core must define what those states mean. [`CompressedSNARK`](https://github.com/microsoft/Nova/blob/01b1e2d662a847ed7029770ecbaf6687398899dd/src/nova/mod.rs) is a separate proof/key path. [Spartan's paper](https://eprint.iacr.org/2019/550) explains computation preprocessing for sublinear verification and why commitment choices matter.

## Three architectures to compare

| Architecture | Ordinary transaction producer | Fresh history verifier | Unresolved central obligation |
|---|---|---|---|
| A: typed incremental execution and compact/shared authenticated evidence | Can use validated reuse, delta work and persistent evidence; unsupported cases fall back | May still traverse a history or derivation DAG unless it has a trusted checked anchor or a succinct history argument | Independent soundness of reuse/coverage; historical verification can still grow with history |
| B: IVC over original full Core semantics | Proves the complete evaluator; full-state checks and old evidence hashing may cost `O(N)` or `O(B_j)` each transaction | Can check accumulated execution without replaying the entire history, subject to proof configuration/public claim | Encoding fidelity and producer cost, not the existence of folding |
| C: IVC over a sound semantic-witness checker plus authenticated memory | Native engine suggests small derivations; circuit/guest verifies them, then folds | Can accumulate the checker's complete semantic claim over history | Checker correctness, omitted-dependency detection, authenticated state/index correspondence and initialization |

**A and C are complementary.** C needs a source of witnesses; A can provide them efficiently. Native reuse alone reduces host cost when the proved relation still performs the same full checks. It reduces circuit work only if the relation is redesigned to verify a sound preservation witness, or if the proved interpreter actually executes fewer checks under verified reuse rules. Merely trusting native `CheckedEvaluation` or a cached Boolean moves authority outside the proof and fails the independent-consumer goal.

For the measured module, an inductive checker could establish positivity for the newly created row while preserving proved positivity for unchanged rows; an authenticated count summary could update by exactly one. Its parent certificate must establish the summary and local-rule claim for the exact parent, schema and module. A complete delta and affected-obligation calculation must be proved. Cross-entity references, query changes and changed global captures can invalidate many old obligations; no universal delta-only bound follows.

## Memory consistency is not semantic completeness

[Nebula, current S&P 2026 version](https://eprint.iacr.org/2024/1605) is directly relevant: commitment-carrying IVC, read/write memory and switchboard circuits address two integration gaps in folding-based machines. The authors [report a prototype and EVM-specific comparisons](https://www.microsoft.com/en-us/research/publication/nebula-proving-machine-executions-via-folding-schemes/). Those are author measurements, not Core speedups. The indexed [original paper §4](https://eprint.iacr.org/2024/1605.pdf) initializes an `M`-cell memory set and describes an `M`-sized final set; continuation links check matching boundary memories. This is not evidence of constant-cost persistent-state boundaries. No clearly designated public Nebula reproduction artifact was located via the paper landing page, MSR page or [author publication list](https://arasua.run/). Full current-PDF retrieval was blocked; indexed original-version passages were used only with that version qualification.

**Core inference:** even a perfect memory argument establishes consistency of accesses to a specified memory. It does not decide that this memory contains every authoritative entity, that a query omitted no member, that all affected rules ran, that historical fresh identities were checked, or that all surviving incoming references were considered. Those obligations belong to the program/checker, its authenticated indexes and initialization proof. Memory checking can make their execution cheaper; it does not supply their semantics.

Two focused memory alternatives deserve investigation only at this seam. A plain Merkle authenticated map provides an easily stated old-root/read/update/new-root relation with explicit path cost; authenticated range/summary indexes must be tied to the complete state. [Volatile and Persistent Memory for zkSNARKs, S&P 2025, revised 2026-09-18](https://eprint.iacr.org/2024/979) explicitly studies committed persistent and sparse persistent memory, rather than zero-initialized volatile RAM alone. That is a relevant comparison for reducing boundary and access overhead; it is not a ready-made proof that Core's MuHash state, historical identity set, reference index and ordered queries all agree. Initialization, finalization, continuation and rebasing costs need separate measurements.

## Witness boundary and the exact statement

A proposed recursive state should bind at least:

- Store/genesis identity, exact history position and chain/event commitment, current module/schema/profile, and execution/checker version.
- Authenticated roots for entity values, historical identity use, reference indexes and all maintained semantic summaries, with a proved correspondence to the authoritative state.
- In-progress request/context and transaction phase, then committed decision/delta/ordered command commitments at the boundary.

The verifier must compare the final public claim against the expected endpoint and policy. A producer may supply arbitrary paths, typed values, summaries, scheduling advice and cached derivations; the relation must authenticate and check them. A private Rust type or trusted native pointer cannot be serialized into a cryptographic proof assumption. Advice that says “these are all query members” needs a completeness argument, not just membership paths for the supplied members.

The checker must preserve exact errors and typed error witnesses, lazy evaluation and skipped branches, signed 64-bit overflow behavior, canonical rule/subject order, first-failure selection, typed captures, absence/negative dependencies, complete-child references, command order and duplicate multiplicity. A field equation is not checked integer arithmetic. Failed evaluation is a distinct output and cannot silently advance the committed-state history. Historical replay under old profiles and current admission/commit authority remain separate.

These are deductions from the [Core persistence contract](../../../../docs/persistence.md), particularly current complete-child validation, exact recovery and durable commands. They are not guarantees imported from Nova.

## Existing SHA-256, canonical JSON and MuHash compatibility

Core's [`muhash.rs`](../../../../crates/behavior-store/src/muhash.rs) incrementally maintains a fraction modulo `2^3072 - 1103717`. Each content hash expands through twelve tagged SHA-256 calls to a 384-byte element; StateId hashes the normalized 384-byte accumulator. [`documents.rs`](../../../../crates/behavior-store/src/documents.rs) defines separate tagged document identities and `HistoryRef`. Thus Core already has an incremental content identity; the problem is proving the required semantic statements about its contents/history.

**Design implications, not measured circuit costs:**

1. Retaining old StateId requires constrained 3072-bit modular arithmetic/range checks, exact expansion and hash tags, and normalization. A prover-supplied inverse is usable only if its equation and representation bounds are checked. This work can be per changed content; it need not recompute every entity's MuHash contribution.
2. Retaining old entity/module/request/event/decision identities requires exactly the old canonical byte mapping and SHA-256 domain separation. A Poseidon/Merkle root is a different identity. Maintaining both roots needs a proved common-source update relation and an initial correspondence proof.
3. Hashing a complete old 4-MB decision inside a proof still processes its encoding. A new compact contract can make the decision an optional deterministic audit projection, but an external consumer cannot treat its old SHA identity as proved unless that correspondence is established.
4. Merkle roots and proof-friendly hashes may be internal evidence identities with versioned bridge statements. That is a design option, not permission to silently replace the external canonical identities. A stronger migration bridge can cost a full-state pass once, with later incremental updates; record which endpoint and module it certifies.

## Compiled-guest comparator, including the fresh Magnetar result

[RISC Zero's receipt contract](https://dev.risczero.com/api/zkvm/receipts) binds a journal to an expected guest image; its [composition documentation](https://dev.risczero.com/api/zkvm/composition) distinguishes conditional receipts from resolved proofs. This is a concrete integration reference for proving an ordinary checker rather than handwriting its whole circuit. A Core guest still needs to bind all public endpoint claims and verify untrusted host data, and its compiled identity must be tied to admitted semantics. No Core guest was compiled here.

[Magnetar's October 2026 paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2026/10/magnetar-1.pdf) describes transparent RV64I proving using binary-field components and standard hashes. Its author measurements concern complete executions, not Core. Crucially, §1.3, printed p.8, says the proposed chunked recursive composition is **not implemented**. No clearly identified public Magnetar source/reproduction artifact or independent audit was located in the reviewed paper/publication/blog pages. The [MSR introduction](https://www.microsoft.com/en-us/research/blog/proof-based-general-purpose-computing-with-magnetar/) is dated 2026-10-15; the accessible paper is dated 2026-10-05. [BinarySpartan](https://eprint.iacr.org/2026/1656) reports direct SHA-256 proving measurements, including witness generation. That makes this line relevant to old hash compatibility, but supplies no measured cost for Core canonicalization, MuHash3072, or accumulated Core history. Treat it as a candidate compiled-guest route with explicit artifact/composition gates, not an already demonstrated replacement for Nova IVC.

## Publication, recovery and module changes

These are proposed protocol requirements; the cryptographic sources do not specify Core's persistence protocol.

| Choice/event | Required behavior |
|---|---|
| Synchronous proof-backed commit | Construct the candidate proof outside the final atomic publication; compare-and-swap the exact parent; durably publish event/support and proof endpoint together. Concurrent losers may waste proving work. State-only equality cannot substitute for history equality. |
| Native commit with asynchronous proof | Expose distinct committed head and proved head. A proof through `k` cannot certify unproved suffix `k+1..n`. Proof-dependent command release waits for the proved endpoint; native-authorized release is a separately stated policy. Monitor backlog/catch-up capacity. |
| Lost acknowledgement/crash | Recover the original exact event and command occurrence IDs. Persist or rebuild prover continuation state from a durable anchor and immutable inputs. A compressed verification proof alone is not demonstrated to recover every witness needed to continue proving. |
| No-state-change commands | Advance exact history and ordered command commitments even when StateId is equal. Duplicate intent occurrences remain distinct. |
| Migration/module switch | Universal interpreter: check authorized module transition, old-to-new state correspondence and all required new rules. Compiled circuits: authenticate new circuit identity and bridge/segment proofs; keep verified old history linked to the exact new genesis state. A universal SRS does not make the old circuit's parameters valid for the new shape. |
| Unsupported optimization | Prove reference full execution, or explicitly reject the unsupported scope. Never accept a host-only fallback while presenting the same independent proof claim. |

Retaining transaction data, expanded-audit reconstruction and independently checking storage completeness remain separate end-to-end obligations; a cryptographic execution argument does not supply unavailable source data.

## Minimal experiment that can reject any candidate

This is a proposed next investigation, not authorized implementation work performed by this report. Freeze the semantic corpus and claim before choosing a cryptographic winner.

1. **One common claim and a tiny but meaningful language slice.** Use entities with `x`, local positivity, bounded global count, a cross-entity reference, checked signed arithmetic, an ordered lazy failure and commands with duplicate occurrences. Include parent validity and exact history. Keep a full reference evaluator and specify the compact witness checker independently. Prove or explicitly leave unproved the checker-equivalence lemma; tests alone are evidence, not that theorem.
2. **Three ways to produce/check the same claim.** A runs the native incremental checker and exports compact derivations; B proves reference full evaluation; C proves the compact checker over authenticated state. For B/C compare a small direct circuit with a compiled guest only where artifacts and execution support exist. Start with transparent Nova/Pedersen-IPA and separately meter compression; add a KZG/MicroNova configuration only with explicit SRS/security scope. Do not silently compare a weaker C claim with full B semantics.
3. **Four independent scaling axes.** Vary `N` at fixed delta; vary affected dependency fanout at fixed `N`; vary history length at fixed state; vary semantic work/microsteps at fixed transaction count. Add one adversarial global query that forces broad work. This separates prior-history independence from current-state/proving cost.
4. **Hash ablation with honest accounting.** Test (i) exact old identities and canonical decision hash, (ii) exact old StateId/history with a new compact decision contract, and (iii) a versioned new authenticated state with an explicit old/new bridge. Record which public identity claim is lost in each mode. Meter SHA/canonicalization and MuHash separately from arithmetic rules and recursion overhead.
5. **Reject bad witnesses.** Omit a member/dependency/affected rule; use an incomplete or stale reverse-reference index; alter request/context/module; forge a count summary or fresh identity; cross a signed overflow boundary; change the selected first error; omit one duplicate command; resume from an equal-StateId but wrong-history anchor; truncate a transaction; present unresolved guest composition assumptions.
6. **Report all producer and consumer work.** Count native instructions/allocations, witness bytes, authenticated accesses, constraints/variables, actual folds per semantic transaction, preprocessing/parameter bytes, first initialization, per-step prover time/RSS, compression time/bytes, standalone verification, full audit export, durable bytes and crash recovery/catch-up. If offline RAM checking is used, include initialization, final-memory work, challenge/commitment phases and epoch boundaries. Separate warm/cold cache and sync/async publication latency.

Evidence for C would be sublinear growth in `N` for a fixed, actually local workload **with all rejection cases preserved**, plus bounded verified-history cost and explicit broad-work fallbacks. Evidence for B would be acceptable producer capacity despite full evaluation and simpler correspondence. Evidence for A would be strong native latency/storage gains with tolerable cold verification. Any candidate can lose on soundness coverage, producer backlog, memory, setup burden, audit availability or recovery costs; no candidate is selected in advance.
