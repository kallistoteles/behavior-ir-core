## Interpretation and limits

A concrete fragment now demonstrates the intended difference: deriving the
finish result and maintaining affected validity/index data can avoid population
and prefix reexecution. BTreeMap/set access still has logarithmic access cost.
The original complete record, identity checks, current/previous-record copying,
output and storage boundaries remain population-shaped and mandatory.

G0 retains acceleration data without reusable selected authorization and pays
actual reestablishment inside the operation. G1 retains already checked exact
facts; V0 still performs ordinary fresh invocation and full original property
checking. The four retained executables have distinct actual bytes and
mechanism-sensitive observations. Negative mechanism tests reject equal-byte
labels and reclassified actual nonprepared executions; they are record-level
controls over actual runs, not a claimed newly compiled malicious-worker proof.

The narrow attempted binding-check shortcut was removed before acceptance:
inspection established that the prepared provider leaves its metadata maps
empty, so that proposed shortcut was not a demonstrated scaling improvement.
Existing Core prepared validation is retained. The actual implementation gains
come from fresh prepared integration, justified validity reuse and maintained
views, while keeping the original format.

No final timing triplets, medians, 50 ms/quarter/80%/110% criteria, integration
recommendation, product trust/finality adoption, cryptographic feasibility or Q6
result is established here. The next phase freezes the completed implementation
and runs the predeclared bounded comparison. A final negative criterion must
remain negative even if this component incrementality result is valid.
