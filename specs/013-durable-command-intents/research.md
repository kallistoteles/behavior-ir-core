# Research: Durable Command Intents

Date: 2026-10-05. Design baseline: Core c62a64c0a23d938a394418b9b78f9e0ddf62b3f2,
release 0.10.2, Rust 1.98.1, Wire IR accepted 0.4–0.7, decision records 0.4–0.6,
verifier 0.6.0 and supported Z3 4.16.0. Feature 012 remains a design dependency,
not a completed implementation. Research agents inspected semantics/verification,
governance and persistence separately; none changed source files.

The decisions below resolve the planning unknowns. They implement the five accepted
clarifications in [spec.md](spec.md). They do not claim the prerequisite fixes have shipped.

## R1 — Semantic version is retained, not inferred from emitted commands

**Decision:** Retain an admitted semantic profile on Module. Wire 0.8 selects the
new profile even when commands and command_effects are empty. New-profile actions
use behavior.action.v2, modules use behavior.module.v2, and action records use 0.7.
Earlier profiles keep their existing admission, runtime, identity and serialization paths.
Builder selection of 0.8 is explicit. Serialization never downgrades that profile.

**Rationale:** [Module](../../crates/behavior-core/src/semantic/module.rs) currently
forgets the input IR version; [serialization](../../crates/behavior-core/src/serialize.rs)
chooses a minimum version from used features. That would erase changed effectfulness
and evidence semantics after a false guard or an empty command collection.

**Alternatives considered:** Infer the profile from nonempty commands; reuse old
identities for 0.8 without commands. Both collapse distinguishable admission/evidence
contracts. FR-017's optional old-record reuse is inapplicable when the new profile applies.

## R2 — Definition bag and value bag are separate

**Decision:** Add command declarations and an action command_effects component.
Declaration fields are a named typed product, canonicalized by UTF-8 field name.
Emission definitions form a finite multiset of declaration identity, normalized guard
expression and payload-expression product. Canonicalize definitions before evaluation
and hashing. Collect successful intent values into a second canonical multiset.
Omitted guard is the literal true guard. Preserve duplicate definitions and values.

**Rationale:** Sorting only final output leaves source-dependent failure selection
and observations. Commands are never inserted into the old ordered state-effect vector.

**Alternatives considered:** Source-ordered emissions; a deduplicating set; independence
analysis of arbitrary effects. None realizes the accepted finite-multiset model.

## R3 — Payload types reuse the lossless scalar domain

**Decision:** Allow Bool, i64 Int, existing exact decimal values, String, Enum,
primitive/fixed-scale Nominal, Id<T>, and one-level Option of a supported scalar.
Empty product is valid. Reject Entity, Query, Exact as a stored payload type, Ref<T>,
nested Option, blobs and new collection/object types. Id<T> creates no live reference
edge. Exact intermediate expressions require a lossless conversion or explicit rescale.

**Rationale:** The existing typed storage conversion is sufficient. A request is immutable
data and must not depend on a live entity object or secretly introduce referential integrity.

**Alternatives considered:** Arbitrary JSON; storing unevaluated expressions/rationals;
Ref<T> with implicit existence checks. These add semantics beyond FR-004.

## R4 — Canonical evaluation and semantic evidence

**Decision:** Preserve the existing incoming-check/precondition/state-effect order;
then evaluate command definitions against original S in canonical definition order,
before final state invariants/postconditions. Guard precedes payload; payload fields
use canonical name order. A construction error aborts evaluation. Only ALLOW exposes K.
All 0.8 semantic evidence uses resolved hashes/normalized binders and structured errors.
Source locations, expression spelling and equal-definition alias display names stay in
a separate diagnostic result, outside candidate/commit identity and semantic replay equality.
Identity equivalence ≡₀.₈ is the relation generated by the specification's explicit
normalization laws, with canonical semantic form equality iff equivalence. Public names,
types, expressions, multiplicity and existing ordered components remain semantic; equal
output for one invocation is not general program equivalence. Hash conclusions remain
conditional on collision resistance rather than claiming mathematical hash injectivity.

**Rationale:** [record comparison](../../crates/behavior-core/src/record.rs) currently
compares source locations; [pretty printing](../../crates/behavior-core/src/pretty.rs)
can reveal lambda or alias names excluded from expression identity. Removing loc alone
would not establish equal-BehaviorHash semantic-observation equivalence.

**Alternatives considered:** Keep IR iteration order; collect errors independently;
strip only command loc. Canonical fail-fast evaluation is the smaller faithful model.

## R5 — Hash encoding and historical type evidence

**Decision:** Keep the existing SHA-256(tag || 0x00 || body) construction. New semantic
definition/value bodies use checked length-prefixed encodings based on the existing
type/value encoder. Document bodies use the existing float-free canonical JSON.
Order emissions by (emission hash bytes, canonical semantic bytes), and intent values
by (intent hash bytes, canonical typed bytes), preserving multiplicity. Hash assumptions
are collision resistance, not mathematical collision impossibility.

A new action record carries a deduplicated historical declaration/type descriptor table
for its emitted intents. Data replay validates those descriptors and canonical values
without the current module; Behavior replay additionally reproduces them from the exact module.
Lengths/counts fail on overflow; no saturation or empty-string hash fallback is allowed.

**Rationale:** A declaration hash alone cannot type-check historical payload data.
[Hashing](../../crates/behavior-core/src/admit/hash.rs) and
[canonical JSON](../../crates/behavior-core/src/canonical.rs) provide existing primitives.

**Alternatives considered:** Current-module lookup during data replay; JSON floats;
source indices; an encoder silently saturating lengths. These break identity or replay.

## R6 — General trusted governance precedes 013

**Decision:** Add versioned evidence_policy.v2, store_genesis.v2, policy.v2,
authorization.v2 and verification_envelope.v2 contracts. Reuse the existing
ed25519-dalek 2.2.0 dependency and strict verification. Sign a purpose-separated message
containing the content hash; issuer identity is inside content and signature outside it.
Commit recomputes policy compliance from a complete authenticated evidence package.
Authorization keys and verification keys have separate policy-defined roles.

**Rationale:** [Current governance](../../crates/behavior-verify/src/governance.rs) and
[store evidence checks](../../crates/behavior-store/src/store.rs) establish self-hash
integrity but not producer authority; cited documents are optional. The existing waiver
cryptography supplies the needed primitive. Strict key/signature verification behavior
is documented by [ed25519-dalek 2.2.0](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict).

**Alternatives considered:** CommandAuthorization; mutable host key configuration;
signature-only ALLOW; trusting any self-hashed verification report. These fail FR-039/040.

## R7 — Trusted verification is fresh and obligation-complete

**Decision:** The trusted verification path derives the expected check manifest from the
admitted subject/profile/encoding version, runs supported Z3 with no disk cache, validates
exact obligation coverage and aggregate outcome, then signs a typed result. The API cannot
turn arbitrary supplied JSON into a trusted verifier-produced result. Migration subject
identity binds exact source and target BehaviorHashes, not only SchemaHashes.
Required unresolved findings block unless the exact execution policy permits a valid waiver.
Envelopes archive the full selected profile and signed closed obligation manifest. Data
replay checks identities, signatures and report coverage without the module; it does not
claim to derive the obligation set. Commit and Behavior replay derive and compare it from
the exact admitted subject.

V2 signs a semantic verification_report.v2 projection, not the raw current report whose
checks/findings include loc/explanation/cache metadata. Keep typed witnesses and semantic
subjects/results; detach diagnostic provenance, including legacy witness-record spelling.
Canonical SMT symbols and result ordering derive from admitted semantic identities/sites.
Raw legacy reports/keys remain unchanged.

The closed manifest is a versioned finite set of exact descriptors with unique site keys.
Descriptors bind subject/profile/versions/category/owner/phase/tagged canonical syntax path/
predicate kind. Repeated command definitions use canonical multiplicity indices; repeated
expression sites use child addresses. Never deduplicate distinct sites or reduce duplicate
keys first/last-wins; shared findings cannot erase check coverage. The obligation/manifest/
report domains and exact hash bodies are fixed in governance.md.

Authenticate only reproducible semantic results. WallClockGuard/cancellation/process/transport
or non-reproducible prefix results abort with an infrastructure error and no signed report;
preserve existing --out files. Deterministic resource exhaustion may be INCONCLUSIVE.
Signing an honest timeout does not make it reproducible or eligible for a waiver.

**Rationale:** [Cache::get](../../crates/behavior-verify/src/cache.rs) currently trusts
a matching check key. Signing a report produced from that cache preserves the forgery path.
An omitted check collection must not become a vacuous proof.

**Alternatives considered:** Sign current cached reports; sign caller-supplied reports;
implement authenticated per-check caching now. The first two are unsound; the third is
unneeded performance work for the prerequisite.

## R8 — Explicit time, trust roots and legacy adoption

**Decision:** Trust keys/policy hashes are immutable genesis data. Key validity intervals,
when configured, use signed explicit UTC time and real-calendar validation; intervals are
[start,end). No clock/environment/network or live revocation lookup enters policy judgment
or replay. No requirement means no required authorization. An empty trusted-authority set
is a valid deny-all policy when authorization is required, never a structural fallback.

TrustedAuthorization(P,A,T,Q) binds the independent explicit context Q alongside candidate T.
Full Q/ContextHash are signed/archived; Q holds policy_time, requested commit time or null and
an exact execution-policy-declared Bool/i64/String product. All role intervals/waiver expiry
use policy_time=authorized_at. Bind commit time iff policy requires it; otherwise null.
Use commit_with_context/prepared-migration context arguments so live comparison cannot copy
Q solely from signed evidence. Context-less governed fresh writes fail; exact recovery uses
original archived Q. No real-world freshness guarantee or current-clock lookup is introduced.

Legacy v1 required-authorization stores retain readable/replayable structural history and
idempotent read-only recovery. New governed writes fail with TRUSTED_GOVERNANCE_UPGRADE_REQUIRED.
Adoption validates/export-checks an exact snapshot and creates a new v2 store with a deliberate
policy and new StoreId. All profile0.8 commits use v2 genesis, even when commands are empty;
legacy none-policy state-only paths retain their original formats. Old lineage/history is
retained; adoption does not preserve history
position, revisions or removed-identity lifetime across lineages. No in-place policy mutation.

**Rationale:** [EvidencePolicy/genesis](../../crates/behavior-store/src/documents.rs)
are immutable, and v1 contains no authorization-authority keys. A new lineage is honest;
silently assigning trusted meaning to v1 is not.

**Alternatives considered:** Host-supplied keys at open; mutate genesis; invent a policy
migration operation; add live revocation. Each introduces hidden or new semantics.

## R9 — Exact evaluated history and one atomic persistence primitive

**Decision:** Introduce HistoryRef(store,state,position,record), commit_bundle.v2 and
transition_record.v2. Commands remain in the canonical decision record inside the atomic
commit record. Bind evaluation and authorization to full HistoryRef; validate it before
rederivation and use its record hash for backend CAS. Reuse one Backend::commit for every
transition. Command-only commits have empty version/index deltas and advance history only.

**Rationale:** Existing backend CAS already uses Head.last_record, but the evaluated bundle
binds only StateRef. Equal state/position on diverged copies otherwise accepts the wrong parent.

**Alternatives considered:** Separate outbox writes/tables; synthetic state changes;
replica IDs; checking StateId alone. All weaken atomicity or identity.

## R10 — Occurrence identity is derived after commit

**Decision:** Hash behavior.command_occurrence.v1 over canonical JSON containing store,
commit_record_hash, intent_hash and multiplicity_index. Position stays enumeration evidence.
Neither candidate record nor committed record contains occurrence IDs. Exact copied history
reproduces identity; divergent commits differ even after state convergence.

**Rationale:** This is clarification 4 and avoids a hash cycle or a genesis/position collision.

**Alternatives considered:** Position-only anchor; source emission number; replica/node IDs;
feeding occurrence IDs into the committed record.

## R11 — Enumerate whole committed events through a pinned head

**Decision:** Store::commands_since takes an exclusive HistoryRef, optional through HistoryRef,
and max_records (default 256; range 1–1024). Pin the observed committed head once. Scan whole
history events, including command-free events and migrations; return all commands in each
scanned event. Return next_after and complete. Continue against the same observed_head.
One commit can produce a large page; max_records is not an output-byte bound.

**Rationale:** Position checkpoints must never strand duplicate commands in a partially read
commit. History is the authoritative outbox, regardless of a derived command index.

**Alternatives considered:** Command-offset cursors; skipping empty pages without advancing;
index-owned enumeration; a moving head on every continuation.

## R12 — Replay validation and backend trust

**Decision:** Share chain/range/endpoint validation between data replay, Behavior replay and
command enumeration. Reject wrong genesis/state/head endpoints, omitted/broken records and
malformed canonical command evidence. No external executor API enters Core. Persistent
process-recovery evidence comes from a test-only host backend in the external consumer,
not an in-memory reopen test. Completeness/atomic crash-safe storage remain backend contracts.

**Rationale:** [Behavior replay](../../crates/behavior-store/src/replay.rs) currently omits
final-state/chain checks. Finite conformance can detect violations but cannot make an
adversarial backend trusted.

**Alternatives considered:** Claim in-memory reopen proves durability; current-state replay;
a Core filesystem backend or dispatch trait just for this feature.

## R13 — Soundness blockers precede trusted claims

**Decision:** Track these prerequisite repairs with failing regression evidence:
nested/exact/rescale/fold bound coverage; read-alias cardinality in whole-module proofs;
behavior-valid incoming snapshots (not schema equivalence alone); exact migration behavior
context; replay endpoints; malformed record hash fallback. New 0.8 payload safety must cover
all reachable dependencies and match guard/canonical fail-fast runtime paths. Unsupported
proof obligations yield INCONCLUSIVE or conservative refusal, never PROVEN.

Preserve earlier IR admission/runtime algorithms and valid historical fixtures. Where a
historical defect cannot be repaired without changing them, conservatively block its proof
in the new verifier contract instead of reinterpreting old modules. A verifier version bump
permits corrected proof outcomes; old published attestations are retained but not accepted
as current trusted evidence. The plan does not claim all audit findings are fixed.

**Rationale:** Cryptographic provenance does not repair a false theorem.
See [bounds](../../crates/behavior-core/src/admit/bounds.rs),
[read encoding](../../crates/behavior-verify/src/reads.rs),
[migration application](../../crates/behavior-core/src/migration/apply.rs) and
[read records](../../crates/behavior-core/src/read.rs).

**Alternatives considered:** Waive semantic-unsoundness bugs; sign existing PROVEN results;
make all audit improvements part of 013 without a dependency/scope boundary.

## R14 — Supported surfaces and versions

**Decision:** Extend behavior-engine explicitly and its public-surface manifest; do not make
internal crates integration APIs. Keep the CLI store-free. Existing invoke/replay/verify
commands support the new semantics; additive trusted-governance commands handle authentication.
A consumer example proves invoke → authorize → commit → enumerate → mock adapter and persistence.

Reserve Wire0.8, decision0.7 and verifier0.7.0 against the current baseline; if a prerequisite
consumes a version, choose the next unused version explicitly before code, never reuse a tag.
Expected Core0.12.0 remains provisional until 012/prerequisite release sequencing is known.
New document tags are enumerated in [identity-and-records.md](contracts/identity-and-records.md).
Use the unchanged scripts/gates.sh list and exact-revision consumer release verification.

**Rationale:** [012 contracts](../012-unified-invocation-model/contracts/engine-api.md)
already unify invocation; [CLI](../012-unified-invocation-model/contracts/cli.md) has no store.

**Alternatives considered:** New invocation grammar; persistent-store CLI; a supported local
dependency override; silently changing an existing format/attestation/cache contract.
